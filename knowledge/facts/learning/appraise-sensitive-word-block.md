# 评价触发的敏感词拦截

## 事实

家长提交课程评价 / 教师评价时内容会经过**敏感词过滤**，命中后统一拦截并提示
「**内容涉及潜在风险，请修改后提交**」。

提示里**故意不展示命中的具体词**。需求文档写明了原因：直接展示会让用户用变体绕过词库；
也容易被截图曲解——比如写「课程有一定难度」被提示「难度」违规，会被理解成"只让写好评、不让说课难"。

**过滤与文案在服务端，客户端不含敏感词逻辑**：鸿蒙代码里搜不到「敏感词」「内容涉及潜在风险」。

**已展示的评价**（展示侧，是另一套处理）：

| 判断层 | 命中后的处理 |
| --- | --- |
| **集团**判断命中 | **整条隐藏** |
| 培优**自定义**命中 | 把敏感词替换成 `*`，其余内容照常展示 |

**审核提示的文案演进过两轮**（用户对着不同版本的提示来问时，别当成不一致）：

| 时间 | 头像审核失败 | 评价审核失败 |
| --- | --- | --- |
| **2024-06 之前** | 「您上传的头像**涉及违规不良信息**，请重新上传」 | 「**评价用词不当**，请修改～」 |
| **2024-06** | 「您上传的头像**不符合平台规范**，请重新上传」 | 「您上传的内容，**不符合我们平台的内容规范**，为维护积极健康的在线教育环境，辛苦您重新上传」 |
| **2026-06** | —— | 统一成「**内容涉及潜在风险，请修改后提交**」 |

**2024-06 那次改动的起因**：**小天才手表因敏感词审核形成了舆论热点**，集团安全团队要求把所有
UGC 审核提示（**用户头像、用户姓名、评价信息**）的措辞从「违规不良信息」这类**硬判词**改成
「不符合平台规范」——**降低对抗感**。
（**姓名**审核失败当时**没有提示文案**，所以那次没调。）

提交侧的提示后来被统一成了固定文案，但**展示侧的这两条规则来自更早的版本，未被覆盖**。

代码位置（鸿蒙侧，只有评价入口）：

| 场景 | 文件 |
| --- | --- |
| 课程 / 场地评价 | `XesCourseCenter/src/main/ets/courseAndVenueAppraise/AppraisePage.ets` |
| 教师评价 | `XesCourseCenter/src/main/ets/teacherEvaluation/EvaluationPage.ets` |
| 评价模型 | `XesCourseCenter/src/main/ets/components/viewmodel/AppraiseBean.ets` |

## 判据

用户报「评价提交不了 / 提示内容涉及潜在风险」时：

1. 这是**敏感词拦截的正常提示**，不是系统故障；
2. **提示不会告诉你哪个词违规**——设计如此。别去客户端找"具体违规词"的逻辑，那不在客户端；
3. 确需定位命中词时走测试排查工具（需求文档提到后台有）。

## 例外

- 需求范围是**培优 APP**，其他端未核对；
- 词库有两个来源——集团合规（固定化文案）与培优自定义关键词（返回命中词），
  本次统一成固定文案的是**培优**这一侧。

**客户端代码核对结果**（仓库 `xesapp`，分支 `releaseV/20260921`，2026-09-22）：
「内容涉及潜在风险」「敏感词」**零命中**，评价入口命中 `XesCourseCenter` 的评价页与模型文件。
即**入口在客户端、过滤与文案在服务端**——这条边界单靠搜索得不出来。
