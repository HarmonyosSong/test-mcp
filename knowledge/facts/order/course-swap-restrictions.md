# 换商品 / 转班的支持范围

## 事实

「换商品」（把已购商品换成另一个）与转班的支持范围**有限制**。

**支持的场景**：

| 场景 | 是否已过课时 | 支持 |
| --- | --- | --- |
| 商品换商品 | 未过课时 | ✅ |
| 班级换班级 | 未过课时 | ✅（一期已有） |
| 班级换班级 | **已过课时** | ✅（二期新增） |

**链路怎么走，取决于「排课 / 生班 / 开课」走到哪一步**：

| 已提交排课 | 已生班 | 已开课 | 走法 |
| --- | --- | --- | --- |
| ❌ | ❌ | ❌ | **商品 A → 商品 B**（直接换） |
| ✅ | ❌ | ❌ | **排课单处理**：撤销原商品排课单 → 换新商品的排课单；已排课的还要**释放原课表与教师资源** |
| ✅ | ✅ | ❌ | **班级 A → 商品 B → 班级 B**：排课成功 → 学员确认 → **开新班 B → 转班 → 原班学员清退 → 原班关闭、释放资源** |
| ✅ | ✅ | ✅ | 已开课的另做特殊处理 |

**关键**：在**已生班**的场景下，"换商品"其实是**绕道转班 + 关原班**——
所以用户会觉得「我只是换了个商品，怎么班级、老师都变了」。

**一期的硬限制**：更换范围只覆盖**授课类型 / 分类 / 学科**，
且「**课次数与分期必须相等**」（不相等就不给换）。
⚠️ **这条后来放开了**——二期起改成「**只支持少变多、分期只支持 1 期变 2 期**」
（见下方「属性调整的限制」）。**两处口径不同，按时间对**，别把它们当成同一版规则。

**产品类型的组合限制**：

| 原 → 目标 | 支持 |
| --- | --- |
| 短期班 / 活动类 → 长期班 | ✅ |
| 长期班 → 长期班 | ✅ |
| 短期班 → 短期班 | ✅ |
| **长期班 → 短期班** | ❌ **不支持** |

**授课类型之间的互转**：**面授与托管之间不可互转**——两者**分别与「在线」做正向 / 逆向互转**
（班课侧的 OMO 转班同时只支持面授、托管课程的课次切换）。

**换商品后的课次怎么排**——两套机制，看产品类型的组合：

| 原 → 目标 | 机制 | 说明 |
| --- | --- | --- |
| **长期班 → 长期班** | **占位制** | 课次拆成 **已过课次 ＋ 正常履约课次 ＋ 待排课次**；两边的**总课次数必须相同** |
| **其余受支持的组合**（短期班 / 活动类 → 长期班、短期班 → 短期班） | **重排制** | 与**新购相同**——有多少课次就排多少个 |

- **已过课次**：原商品有已过课次时，目标班要开出**对应数量**的已过课次（二期起支持）；
- **待排课次**：目标商品**选不满**剩余所有课次时，盘古侧支持**少选**，
  选不满的那部分就变成「**待排课次**」。

**「课次不一致」的 OMO 转班**（2026-04 起，用于单双周互转）：

济南因当地高中的上课形式，存在**单周、双周两种长期班**——学员续报时选错（报了单周、实际只能上双周），
原来只能**退班重报**；现在支持**课次不一致的 OMO 转班**，**多退少补**。限制条件：

- **按「分校 ＋ 业务线 ＋ 年级」配置生效范围**；
- **开课前**才能操作（`开课时间 − 当前时间 > 0`）；
- 必须**同期班**，且**分期数相同**；
- **仅 C 端支持**（APP / 小程序）；
- **一个报名最多操作 2 次**；
- 产品类型 = **长期班**。

**价格算法**：按原班与目标班**每个分期的财务记录**分别算**多退**和**少补**，再综合；
若同一报名下 2 个分期里**一个要缴费、一个要退费，先拦截**（业务上理论上不存在这种情况）。
**发生互转时，原班的调课会被取消。**

**属性调整的限制**（当时口径）：

- **分期课次数**：仅支持**少变多**（原班 1 期 3 节 → 目标班 1 期 7 节）；
- **分期数**：仅支持**1 期变 2 期**；
- 过课时转班时目标班会做**空课次填充**（只为开班用），因此**待付款页的课次数要显示「转班课次数」，
  而不是目标班总课次**。

## 判据

用户说「想换商品 / 换不了」时：

1. **先看产品类型组合** —— **长期班换短期班不支持**；
2. **看课次数与分期数** —— 只支持少变多、1 期变 2 期；
3. **课次数显示** —— 换商品订单在待付款页显示的是**转班课次数**，不是目标班总课次（刻意的，避免误导）。

## 例外

- 规则来自 2024-01 的二期需求，后续可能放开；
- 换商品涉及订单系统改造，客户端只做展示兼容。
