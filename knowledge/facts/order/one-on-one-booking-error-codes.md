# 1对1 自助报名的错误码与文案

## 事实

1对1 C 端自助报名链路（预约 → 预课表选班 → 报名 → 下单 → 缴费）里，服务端错误码会被归成固定文案
返回给用户。**文案与真实原因经常对不上，排查以错误码为准**：

| 服务端错误码 | 真实原因 | C 端归类 | 用户看到的文案 |
| --- | --- | --- | --- |
| `910008` | **第一次上课时间距当前不足 48 小时** | 商品报课要求 | **没抢到，看看别的吧~** |
| `910016` | 第一次上课时间小于 %s 小时 | 同上 | 同上 |
| `910013` | 学员已有该商品同一时段的课表 | 学员问题 | 您在该时段已有学习安排，请勿重复提交！ |
| `910011` | 商品不存在 | 商品异常 | 提交失败，请重试~ |
| `910033` | 商品年部未配置排课规则 | 商品异常 | 同上 |
| `910034` | 商品未配置年部 | 商品异常 | 同上 |
| `910003` | 计算预排时段为空 | 系统异常 | 同上 |
| `910012` | 教学点参数必填 | 系统异常 | 同上 |
| `999999` | 系统异常 | 系统异常 | 同上 |
| `910001` | 教师资源不足 | 资源无法用 | — |
| `910002` | 教室资源不足 | 资源无法用 | — |

**最容易误判的一条**：`910008` 让用户看到「没抢到，看看别的吧~」——听起来像名额被抢光，
**实际是首课时间不满足 48 小时排课要求**。顺着"库存 / 并发竞争"排查会完全跑偏。

## 判据

用户报「1对1 报名失败」并给出文案时：

1. **先按上表把文案反查成错误码**，别按文案字面理解；
2. 「没抢到，看看别的吧~」→ 查首课时间是否 <48h（`910008`），不是查库存；
3. 「您在该时段已有学习安排」→ 学员已有同时段课表（`910013`），业务校验而非系统故障；
4. 「提交失败，请重试~」是个**大杂烩**——商品不存在、年部未配置、系统异常都落到这句，
   必须拿到错误码才能区分。

## 例外

- **错误码与文案的处理都在服务端**：鸿蒙客户端搜 `910008`「没抢到」等全部零命中，
  客户端只展示服务端返回的结果——别在客户端找映射逻辑；
- 表内映射出自 PRD 的 C 端需求表，是设计/联调时的约定，可能与线上最新实现有偏差。
