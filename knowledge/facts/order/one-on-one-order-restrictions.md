# 1对1 订单的几处刻意限制

## 事实

业务归属 = **学而思1对1** 的订单链路有**几处刻意的功能限制**，用户自助不了不是故障：

| 位置 | 限制 | 原因 |
| --- | --- | --- |
| **待付款页** | **屏蔽「取消订单」按钮**（保留「立即支付」跳收银台） | 业务不期望家长自行取消 |
| **已付款页 - 申请退款** | 点「尝试转班」**不跳转选择目标班**，提示「**请联系顾问或班主任完成转班**」 | 1对1 转班走人工 |
| **购课单** | **不展示「缴费开始时间」** | **长期班 / 续报催缴**场景下 1对1 学员不能主动在 APP 下单、到时间也无法操作，业务希望逐个催缴，展示无意义<br>（**这是 2025-04 的口径**；1对1 **短期班**的 C 端自助购买是 **2026-02/03** 才开放的，见 [[one-on-one-c-end-purchase]]） |

**这三条限制有同一个根因——1对1 全链路本来就走人工**：

- 1对1 的**课程 / 班级不是后台直接建的**——**1人班 / VIP托管**走「**商品 - 班课流程**」，
  **禁止在一站式班课平台直接创建**（新增课程 / 班级会被拦「不支持创建」，
  历史存量数据的**创建审核**也会拦）；**只有 8 人班**走正常班课流程；
- **变动要求「有学员」**：有学员的走**排课校验**（拉学员信息发起排课）；
  **无学员的不允许变动**，提交变动或审核时直接拦「不支持变动」；
- 角色分工上，**主讲有日历、要参与排课资源校验**；**辅导（班主任）没有日历**，
  只做课程售卖相关服务——所以**预约、转班、取消这些动作都落在顾问 / 班主任身上**。

理解了这一点，上面三条就都顺了：**不是客户端漏做了功能，是业务没有把口径放给家长**
（这一段是**文档口径**，不是代码验证出来的）。

**转班订单要在 2 小时内支付**：转班订单**有超时倒计时**，文案是「请在 `X天X小时X分X秒` 内完成支付」，
**业务上的实际超时时间是 2 小时**。而这两类订单**刻意不显示倒计时**：

- **1人班商品** 与 **8人班班级** 的**续报订单**；
- **1人班班级** 与 **8人班班级** 的**二段催缴订单**。

所以「这个订单怎么没有倒计时」是**按场景设计的**，不是漏显示。

**「取消订单」这条到 2026-03 仍未放开**：业务确实提过「续报支持用户在 C 端取消订单重下」，
但文档给的结论是「**业务方案不清晰，暂不支持**」——
所以屏蔽取消订单**不是历史遗留，是持续的口径**，别按"迟早会放开"来推断。

另外，**8 人班的转班**也曾在「我的-转班-我的课程列表」被屏蔽（后补齐到退费流程，因为最初漏了）。

代码位置（鸿蒙侧）：

| 环节 | 文件 |
| --- | --- |
| 待付款页（取消订单及确认弹窗） | `XesOrder/src/main/ets/components/orderBusiness/BeforePayPage.ets` |
| 退款申请 | `XesOrder/src/main/ets/components/refund/RefundApply.ets` |
| 购课单 | `XesOrder/src/main/ets/components/shoppingCart/` |

## 判据

用户说「取消不了订单 / 转班要联系顾问 / 没有缴费时间」时：

1. **先确认是不是 1对1**（业务归属 = 学而思1对1）——是的话三条都是**设计如此**；
2. **取消订单** → 1对1 待付款页**没有**取消按钮，需顾问 / 班主任操作；
3. **转班** → 1对1 不给自助，提示语就是「请联系顾问或班主任完成转班」；
4. **缴费时间** → 1对1 购课单刻意不展示，不是数据缺失。

## 例外

- 「8 人班转班屏蔽」是另一条独立限制（覆盖转班与退费两处）；
- 版本兼容原则写明端上改动**老版本可维持现状**——新旧版本行为可能不同。
