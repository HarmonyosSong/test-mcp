# 盘古扫码支付（二维码为什么老出问题）

## 事实

**盘古顾问支持自助下单**时会**按支付方式生成一个支付二维码**，引导学员扫码支付。
但这条路有两个**平台侧的硬约束**：

1. **微信会按主体封禁二维码**；
2. **微信风控不允许「截图扫码直接进入收银台」**。

结果是**频发"微信无法付款"**、阻塞支付流程。所以 2025-05 起改成：**扫码后先进一个「订单详情确认页」H5**，
用更官方的订单信息确认来**解除风控**、提升信任感与缴费成功率。

**这个 H5 页面的规则**：

| 项 | 规则 |
| --- | --- |
| **覆盖范围** | **非 1对1** 班级扫码**均进这个页面**（页面架构参考 1对1 的订单详情 H5） |
| **岗位展示** | **非彼芯**：主讲 → 岗位名「**授课**」、辅导 → 「**辅导**」；<br>**彼芯**：主讲 → 岗位名「**教练**」、辅导 → 「**辅导**」（没有则展示空） |
| **上课地点** | **在线课不展示**该字段 |
| **支付方式** | 按**扫码的端**展示，由服务端做过滤 |
| **浏览器扫码** | **默认展示支付宝**支付，并吊起支付宝 |

扫码前的二维码上展示「【学生姓名】的订单」与**课程顾问（报名人姓名）**。

## 判据

用户 / 顾问说「**扫码付不了 / 微信打不开**」时：

1. **先确认扫码的端** —— **浏览器扫码默认走支付宝**，微信里打开才会有微信支付；
2. **「截图发出去扫不了」** —— **微信风控刻意不允许**截图扫码直接进收银台，这是平台限制，
   不是我们的二维码坏了；
3. **「二维码被微信封了」** —— 微信会**按主体**封禁，属于已知问题，所以才改成先落订单确认页；
4. **1对1 不走这条路**（这个页面明确是**非 1对1** 的）。

## 例外

- 需求方是**盘古**（顾问侧发起），但**家长是扫码方**——C 端报障会落到这里；
- 「在线课不展示上课地点」与详情页的其他地点规则一致（见 [[online-lesson-in-offline-class]]）；
- 支付方式过滤在**服务端**，客户端只按下发展示。
