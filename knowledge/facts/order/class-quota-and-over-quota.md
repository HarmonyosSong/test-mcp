# 班级名额的四种口径

## 事实

「这个班还有没有名额」**不止一个数**——班课侧一共**四种**名额来源，各自独立生效：

| 口径 | 配在哪 | 作用范围 |
| --- | --- | --- |
| **班级限额** | 班课平台 - 课程 / 班级管理 | **不限渠道**，整体可报名的人数（基础名额） |
| **课程 / 班级超限额** | 班课平台 - 班课工具 - 班级超限额管理 | 在**设定的时间范围**内，**不限渠道**可额外报名 |
| **虚拟限额** | IT 在【全局参数管理】配值 ＋ 业务在【网报时间管理】配时间 | 在配置范围内不限渠道可额外报名（**目前只有成都、重庆有值**，其它均为 0） |
| **岗位限额** | IT 在【全局参数管理】配「角色 → 超额数值」 | 按**用户角色**判定（读盘古、呼叫等平台的用户角色），识别其**是否有超报权限** |

**岗位限额是分档的**：主管 `1` / 初级 `2` / 高级 `3`，每档数值不同。

**托管班的超报是「能力支持、业务口径统一关闭」的**：2025-01 业务确认
「托管**统一关闭**云听课和超报」（云听课见 [[class-replay-and-cloud-listening]]）；
系统侧同期把**托管**加进了超限额管理的授课类型里（在此之前只有**面授 / 在线 / 双师**三种）
——所以托管班在后台**可以配**超限额，但**默认口径是关**。

**为什么这条重要**：

- 家长看到「已满」但**顾问还能报** → 不是 bug，是**岗位限额**（顾问角色带超报权限）或**超限额时间范围内**；
- 反过来，**业务可以按班关掉超报**——需求里专门做了「**岗位限额开启 / 关闭**」，
  **线上历史数据默认开启**；
- 顾问之间"**你能报我不能报**" → 是**角色档位不同**，不是数据问题。

**超限额的管理规则**（后台）：

| 项 | 规则 |
| --- | --- |
| 人数 | **正整数，上限 1000**；导入时执行**覆盖**逻辑 |
| 日期 | 默认**开始日 00:00:00 ~ 结束日 23:59:59** |
| 授课类型 | **只支持 双师 / 面授 / 在线 / 托管** 四种 |

**限额是分层级的**：**课程限额 ≥ 该课程下所有班级限额之和**——所以业务想扩某个班的班级限额，
得**先扩课程限额**（面授 / 托管改课程限额时会**同步更新班级限额**；在线则要求
所有班级限额 ≤ 课程限额 ≤ 1000000，且**在线不能突破限额标签**）。

**培优另外收紧了标准值**（别处超限额上限是 1000，培优的班级超限额是按档位卡的）：

| 业务线 | 授课类型 | 课程 / 班级限额 | 班级超限额 | 超标准的处理 |
| --- | --- | --- | --- | --- |
| 培优 | **面授 / 托管** | 10、20 | **0、1、2、3、4、5** | **直接拦截** |
| 培优 | **在线**（小班） | 10、20 | **0、1、2** | **直接拦截** |

- 超限额超出标准会**直接拦截**，提示「该班级超限额人数暂只支持 0、1、2」；
- **课程 / 班级限额**超出标准则走**二次审核**——由新增的「**总部班级主管**」角色审批，
  后台多出「创建待二次审核 / 变动待二次审核」两个状态。

**客户端侧只有「剩余名额」**（`XesCourseCenter/src/main/ets/components/viewmodel/ClassDetailBean.ets`），
**没有**「超限额 / 超报 / 名额已满」的任何中文字段——**名额判断全在服务端**，客户端只展示结果。

**⚠️ C 端和 B 端看到的「名额」不是同一个数**（文档原话，这是最容易搞混的地方）：

| 视角 | 名额 = |
| --- | --- |
| **C 端（家长）** | **班级限额** |
| **B 端（客服 / 顾问）** | **班级限额 ＋ 班级超限额 ＋ 虚拟限额 ＋ 岗位限额** |

所以**家长看到"已满"、客服却还能报**，根子是**两边看的数不一样**——
客服的实际额度通常是「**班级限额 ＋ 班级超限额**」。

**客服侧的「剩余名额」算式方向容易看反**——它是**「负名额候补」场景专用**的：
**在班人数 −（班级限额 ＋ 班级超限额）**。
它算出来的其实是「**超额人数**」而不是常规余量：**只有 ≥ 0（班级已满）才允许候补**，
所以取值只接受 **0 和正整数**。别拿它当"还有几个名额"去用。

**怎么按班级关掉超报**（北分提的：教室资源有限、超报容易引发客诉）：

| 手段 | 做法 |
| --- | --- |
| **班级超限额** | **按班级配成 `0`**（现有能力） |
| **虚拟限额** | 让技术支持在【全局参数管理】里改成 `0`（现有能力） |
| **岗位限额** | **按班级关闭**（2026-06 新增；关闭后**即使有岗位限额权限也不能用来报名**） |

## 判据

用户或顾问反馈名额问题时：

1. **「家长说满了、客服还能报」** → **两边看的数不同**（家长看班级限额、客服看四种之和），**不是哪边算错了**；
2. **「显示满了为什么还能报」** → 落在**超限额时间范围**内，或该顾问有**岗位限额**权限；
3. **「顾问报不了」** → 该班的**岗位限额被关闭**，或该顾问的角色不在档位里；
4. **「别的顾问能报我不能」** → **角色档位不同**（主管 1 / 初级 2 / 高级 3）；
5. **别去客户端找原因**——客户端没有名额判断逻辑。

## 例外

- **虚拟限额实际上已停用**（只有成都、重庆配过值，其它为 0）——遇到它优先怀疑是历史遗留配置；
- 四种限额是**不限渠道**的（谁都能占），只有**岗位限额**按角色区分；
- 规则来自 2026-05 的需求，后台能力，客户端搜不到。
