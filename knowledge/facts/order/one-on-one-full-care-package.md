# 1对1 全托课（全托包）

## 事实

**1对1 全托课**是打包售卖的服务模式：**每 28 天一个周期**，
一个课包里含 **1对1课程 ＋ 1对5练习 ＋ 1对N自习 ＋ 模考（待定）**。

**它绕开了一个技术约束才做出来**——自习和练习要 **1 对多**，但全托的时间又得按学员需求**滚动定制**，
四个方案里前三个都被否了：

| 方案 | 结果 |
| --- | --- |
| ❌ 开一个整期班、动态购买班级里的部分课次 | **交易底层不支持一个班级买多次**（很多逻辑是按 `passcount` / `classcount` 算的） |
| ❌ 下单时合流或新开班 | 新的排课开班模式，上下游兼容成本高 |
| ❌ 业务提前把需要的组合班都开出来 | 组合情况太多、开班压力大，开错还要补救 |
| ✅ **下单时按学员需求开「1人班」，但允许给同时段设资源限额、允许多人报进同一老师时段** | 变相实现 1 对多开课 |

**购买入口**：**盘古按规则发起组合购买，C 端不支持**。

**课包里的商品规则**：

| 商品 | 规则 |
| --- | --- |
| **1对1 - 1人班** | 用**无规律商品**；首次课报课日期设成**不限**；时段 / 日期以端上传递为准；**一个课包一个学科对应一个班级** |
| **1对1 - 8人班（自习）** | 不管买几个 1对1 课程，**只开一个自习班**；学科 = **综合**；**限额 1** |
| **1对1 - 8人班（练习）** | 同上——**只有一个练习班**，学科综合，限额 1 |
| **8人班（模考）** | 待定 |

- **一次购买只能买一个课包**；课包里各类商品**都不支持多分期**；
- **1人班和8人班的资源全部占用完成、且 8 人班开出来之后**，才**提交订单**；
- 这类订单与报名要**单独打标**——报名表新增「**全托购买批次 ID**」，供 C 端与盘古展示；
- **订单超时**沿用商品现有规则（按分校 + 年部 + 窗口期读取），**不一致时取短**。

**组合退费是硬要求**：全托课**必须组合退费**——发起退费时，该课包（订单）里
**未过课时的课次要一起退掉（包括加课班），不能单独退某一个班**。
做法是按「全托购买批次 ID」查出**所有组合报名统一退**，**由盘古发起**，
而且**不进待退费列表、直接秒退**。

**优惠**：券按报名匹配、活动按类型匹配；一个订单里同时有商品和班时**各自匹配、取最优**用在订单上，
**不支持商品和班共用同一个活动**。

**报课短信**（本期只定制了这一条）：条件 = **报名场景 = 全托课**，
且**订单中所有商品都完成「转入履约班」动作之后**才发。

## 判据

1. **「全托课在哪买」** → **C 端买不了**，走**盘古**的组合购买；
2. **「能不能只退自习班 / 练习班」** → **不能**，全托课**必须组合退费**，未过课时的课次一起退；
3. **「报完为什么还没开课」** → 要等 **1人班与8人班资源全部占用完成、8人班开出来**才提交订单；
4. **「分期怎么选」** → 全托课里的商品**都不支持多分期**。

## 例外

- **模考**当时**待定**，尚未定型；
- 学习页把课包内多个班级卡片**聚合成一个**的展示方案，当时**还是待定方案**（需求文档标注「版本待定」）；
- 规则来自 2026-06 的版本需求，**以当前版本为准**。
