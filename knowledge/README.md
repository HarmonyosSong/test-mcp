# 问题排查知识库

> **运行时边界**：本文的知识结构、检索流程和 MCP 工具说明适用于当前 `mcp_server/`。聊天产品 Runtime 由 Mastra TypeScript 承载；知识查询记录会话/消息关联，终态诊断 best-effort 归档案例并写入 outcome。真实模型评估、案例复核和知识提案入口见 [`docs/triage-feedback-and-evaluation.md`](../docs/triage-feedback-and-evaluation.md)，当前系统边界见 [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md)。

面向线上问题排查 Agent 的**纯内容仓库**。这里只有 Markdown，没有代码——目的是让懂业务的同学
（一线支持、SOP 负责人）能直接改、直接提 PR，不需要碰 agent 代码。

## 这个库是什么：从用户现象到业务链路的索引

它保存**用户语言 → 业务场景与候选链路 → 代码及证据位置**的映射，并提供区分候选所需的业务判据。
知识库帮助 Agent 理解用户说的是哪件事、该去哪里核实；诊断结论必须结合当前场景和实际证据形成。

条目里**位置要写足，逻辑不要抄**：位置是索引（「没让我签合同」→ 哪两个文件、哪个函数），
抄来的逻辑是副本（代码一改就过期，而 agent 自己读得到）。用户说的「付钱没让我签字」在代码里
可能叫 `signContract`；知识库积累这种术语映射和跨模块关联，减少直接搜索时对关键词的猜测。

## 默认排查路径

**业务现象优先查知识，明确技术线索直接查证据。** 对“付款没让我签合同”这类业务描述，默认流程是：

默认调用 `lookup_issue`：工具内部先查现象，未命中、弱命中或端/版本不匹配时回退到现象与事实的联合检索。
一次返回最多 3 个候选，以及首个候选和直接引用中最多 3 份预览，每份正文最多 1500 字符。
已返回的信息足够定位时直接核实代码；仅在需要的判据或例外被截断时调用 `get_knowledge_entry` 分段读取。
正文默认每页 2000 字符、最多 4000 字符；按 `next_offset` 继续，值为 null 表示读到末尾。
Runtime 保留知识预览和正文页的完整结构，不再统一截成字符串。
预览会明确标注 `truncated`，所有知识预览都是线索，不能充当本次问题已成立的观测证据。

```text
用户描述 + 已知产品、端、版本
   ↓
检索现象条目：识别业务场景、术语和候选链路
   ↓
读取相关事实与判据，复用已有信息；必要时追问以区分候选
   ↓
定位对应仓库、模块、文件与关键符号
   ↓
结合当前代码、日志、接口数据核实
   ↓
形成结论，或明确仍缺少的证据
```

**产品、端、版本是定位上下文，业务场景是连接代码的桥梁。** 只知道产品不能确定问题属于哪个模块；
已知信息应参与范围判断，未知信息保持未知，不猜测、不作为检索的必填前提。存在多个候选时，先利用
已有页面、操作过程、日志等信息区分；仍有歧义，再问能区分候选的问题。

例如，“付款没让我签合同”可能指订单合同，也可能指收银台协议。知识库先指出这两条候选链路及其
代码入口，再根据实际页面和操作过程选择核实位置。**命中某条知识或定位到某个模块，不等于确认根因。**

两种情况需要调整路径：

- **已有明确技术锚点**：完整堆栈、文件路径、关键符号或具体接口错误足以支持定位时，可以直接查对应
  代码和证据；遇到业务语义不清楚，再补查知识库，不强制先检索知识。
- **现象条目未命中**：回退检索事实条目和术语映射（`scope="fact"` 或 `scope="all"`）。仍无有效线索时，
  根据用户已提供的线索做有范围的代码检索，或提出区分候选所需的追问；仅在范围内检索无结果时逐步扩大。
  未命中表示知识覆盖不足，不表示问题不存在，也不应直接跳到无范围的全仓搜索。

> 完整的入库筛选条件见 [docs/decisions/0001](../docs/decisions/0001-knowledge-base-selection.md)。

## 为什么单独一个仓库

- **生命周期不同**：代码按版本发，知识天天改。产品一改版，某条原因就不存在了，不能为了一条
  知识走代码 review 和发版流程。
- **维护人不同**：知识的主要维护者不需要会写 Python。
- **端无关**：同一个现象在鸿蒙 / iOS / Android 上共享一张索引，不该跟着某个端的代码仓库走。

检索代码不在这里，在独立的 `mcp_server/src/harmony_knowledge_mcp/` 服务中。Mastra runtime 通过 MCP 调用该服务；本目录是它加载的知识内容源。

## 知识从哪来

四个来源，按可信度排序，`authority` 字段写的就是它：

1. **xesapp 自己的知识层** —— 代码仓库里的 `harness_Engineering/knowledge/`（`code-map.json`、
   `contracts/*.md`）。那里是团队已经用代价换来的不变量，例如“支付、退款、合同状态码不得凭字段名
   猜测”。**引用它，不要复制它**：他们的治理原则写明“不要新增一份平行模块文档”“二者只能有一个
   语义权威源”。复制一份过来，两处就开始各自漂移。
2. **一线工单与支持团队经验** —— 入库前提炼成“这类现象出现过 N 次，其中 M 次根因是 X”，
   原文不入库。
3. **代码核对** —— 读随版本发布的代码得出的结论，标 `authority: code`，正文写清文件路径与符号名。
4. **知音楼 PRD** —— 拉式蒸馏，不追全量：排查踩到没有事实条目的领域时，才翻该领域的需求文档，
   提炼「用户语言 → 代码位置」的映射。原文留在知音楼，条目里只放链接——
   那个链接是**人工核实入口**，agent 读不到知音楼（也不给它接工具）。

## 和 xesapp 自有知识层的分工

| | xesapp `harness_Engineering/knowledge/` | 本库 |
| --- | --- | --- |
| 回答什么 | 代码为什么这样写、改这里要守什么约定 | 用户这么说，可能是怎么回事 |
| 给谁看 | 改代码的人与 Agent | 一线支持、排查 Agent |
| 组织单位 | 模块、合同 | 现象 |
| 方向 | 代码 → 不变量 | 用户语言 → 候选原因 |

**同一条知识不要在两边各写一份。** 落在他们那边的（模块边界、代码导航、业务不变量），这里只留一句
“以该仓库的 `harness_Engineering/knowledge/` 为唯一权威源”并给出路径，不复述内容。反过来也一样：
这一层独有的东西——用户会怎么描述、什么话对应哪条链路、两边的用词差在哪——他们那边没有，别写回去。

## 目录

```text
symptoms/       现象入口，保持平铺，通过 domains 关联一个或多个业务域
facts/
  account/      账号、登录、授权与隐私设置
  cloudlearn/   云学习、语音评测与其 H5 链路
  contract/     合同、协议与补签
  invoice/      开票
  learning/     课程学习、回放、资料、讲义与评价
  order/        报名、购课单、订单，以及选课链路上的展示规则（课态、名额、教师、优惠、地点）
  payment/      缴费与先学后付
  shared/       确实跨业务复用的容器能力、公共入口
_schema.md      字段、目录与引用约束
AGENTS.md       后续维护知识内容时的执行约束
```

现象和事实按两个目录维护，方便分别管理检索入口和可复用判据；检索器通过 `kind` 和 `scope` 区分它们。

### 业务域如何参与索引

事实固定放在 `facts/<业务域>/<name>.md`，只保留一层业务域，不按产品或端复制目录。
每条事实只有一个主目录；`domains` 可以包含其他相关业务域，但必须包含主目录的业务域。
不填时，事实的业务域从目录推导。`shared` 只收确实共用的事实，不作为暂时不知道如何分类的收纳处。

目录改善维护和导航，**业务域用于同等文本匹配下的排序优先级，不是硬过滤**：

1. 用户描述先匹配现象，结合已有信息及条目的 `domains` 得到一个或多个候选业务域。
2. 读取关联事实，或以 `scope="fact"` 回退检索；已知候选域时传 `domains`，同分时优先这些域和 `shared`。
3. 其他域仍参与检索，文本匹配更强的跨域条目仍可排在前面。无有效命中或匹配较弱时，取消业务域偏好，
   结合已知术语调整查询；业务域不明时直接全局检索，不凭空选域。

例如合同问题可传 `domains=["order", "payment", "contract"]`。不知道有哪些域时可调用
`list_knowledge_domains`；返回的域名来自实际条目。分类命中不改变 `authority`，也不能把线索升级为证据。

新增条目与业务域的具体约束见 [AGENTS.md](AGENTS.md) 和 [_schema.md](_schema.md)。

## 两级结构

```text
用户输入「付款的时候没让我签合同」
   ↓ 匹配 symptom / aliases
现象条目 symptoms/cannot-sign-contract.md
   ↓ 正文引用判据
事实条目 facts/contract/order-contract-agreement-sources.md
```

现象条目里的 `[[fact-name]]` 是引用语法。CI 会校验每一个引用都能解析到真实条目，
引用断了会让一次排查静默失败——这是知识库最常见的腐烂方式，必须机器查。

引用使用全库唯一的 `name`，不带目录，例如 `[[order-contract-agreement-sources]]`。
允许跨业务域引用；移动条目只调整目录和 `domains`，保持 `name` 与文件名不变，引用不需要跟着修改。

截至 2026-09-30，66 条事实均有现象入口，校验会列出后续新增的孤儿事实；事实也能通过 `scope="fact"` 或 `scope="all"` 检索。
定位流程见 [定位 Skill](../skills/locate-app-issue/SKILL.md)，新增入口以真实案例为依据。

召回合并原有短语匹配与受控业务概念扩展（`concepts.py`）：如错题本/错题集、优惠券/代金券，
不依赖完整问句相同，也不降低通用子串阈值。概念命中分数低于精确短语，并按概念覆盖与专一程度排序；
命中短语以 `concept:` 标注。它是有限术语表的语义扩展，不是通用向量语义检索，未知概念仍可能漏召回。
域偏好继续只在同分时生效，弱匹配继续回退全库。新增现象为 `auto` 来源，未虚构人工核验日期。

2026-09-30 增补“错题录入/上传错题”对象表达。legacy 对已召回且共享业务概念的同分候选，
先比较输入/输出动作与 PDF/图片限定的覆盖，再应用域偏好；动作和格式不独立增加候选。
V2 将这些信息作为动作、限定条件参与既有评分，不把“上传 PDF”当作独立业务对象。
“上传/录入/导入”和“导出”分开登记；命中只表示条目讨论该任务，不能推出支持该格式或确认故障原因。

召回维护先补同一条目的业务别名或概念同义表达，不复制事实、不调整域排序来制造命中。
`experiments/knowledge_audit/datasets/legacy-knowledge-retrieval.jsonl` 保存旧 Python Agent 阶段发现的漏召回、额外改写与无关查询；
`agent/evals/test_knowledge_retrieval.py` 是仅供复核历史 Agent 行为的旧评测，不验证当前 Mastra Agent。
额外改写不得原样复制进 aliases；旧评测通过仅说明这些样本覆盖，不能宣称具备通用语义检索能力。

检索与正文预览可分别配置，修改环境变量后须重启产品 runtime 或独立知识 MCP。Mastra runtime 会将这两个变量传给按请求启动的知识 MCP：

- `HARMONY_AGENT_KNOWLEDGE_RETRIEVAL_MODE=legacy` 是默认召回；`v2` 是实验性的有类型词表检索。
  V2 统一比较现象和事实，包含规范 ID 精确查询与场景限定；目前仍有库外误召回和事实别名覆盖退化，
  不应凭合成评测切为默认。`shadow` 尚未实现：独立启动 MCP 时会报配置错误；产品 runtime 中会导致知识 MCP 不可用，聊天仍可在不挂载知识工具的情况下继续。
- `HARMONY_AGENT_KNOWLEDGE_PREVIEW_STRATEGY=ranked` 可独立配合 legacy 使用，只调整正文选择，
  不改变候选及其排序。未设置时，legacy 沿用旧预览，V2 使用 ranked。
  显式设置 `legacy` 可恢复旧预览。仍最多返回 3 篇、每篇 1500 字符；不足的判据与例外按页读取。
  ranked 的第二槽位由直接事实与合格的一跳引用按相关性竞争，同分优先直接事实；
  引用同样受端/版本降权约束，不能因属于引用就绕过适用性。
- 响应与查询日志记录 `preview_strategy`，快照标识包含策略。所有预览都是线索，
  `ambiguous`/`leads_found` 表示检索状态，不是根因确认，也不提高条目权威。

调整依据与冻结样本结果见 [V2 调整评测](../experiments/knowledge_audit/REPORT-V2-ADJUSTMENT-2026-09-28.md)。

## 写一条知识的自检

> **如果模型忘了这条，它会答错吗？**

会 → 该入库。不会 → 它在占位置。

## 明确不该入库的

- **把代码逻辑抄成自然语言** —— 那是副本，代码一改就过期，而 agent 自己读得到。
  反过来，**位置**恰恰是索引的核心，要写足（文件路径 + 符号名），别只写「见 XX 模块」
- **某一次诊断的中间过程** —— 那是案例，是数据
- **排查步骤清单** —— 那是 Skill，不是知识
- **历史工单原文** —— 那是数据。要提炼成“这类现象出现过 N 次，其中 M 次根因是 X”再入库
- **xesapp 自有知识层已经写过的东西** —— 模块边界、代码导航、业务不变量在他们那边，引用即可
- **未经人工验证的模型结论** —— 可以入库，但必须标 `authority: auto`、不填 `verified_at`，
  让检索侧看得见它是线索而不是结论

## 校验

```bash
uv run --project mcp_server harmony-knowledge-validate
```

校验目录层级、业务域字段、frontmatter 完整性、全库 ID 唯一、名称与文件名一致、跨域引用可解析，
并报告超过 180 天未验证的条目。`make test` 也会执行这项内容校验。

## 诊断反馈与提炼

当前 `mcp_server/` 提供知识查询日志和知识库校验入口；Mastra runtime 会将会话/消息 ID 传给知识 MCP，
并在诊断终态 best-effort 归档案例、独立追加 outcome。通过 `make live-eval` 执行 provider-backed 固定集评测；
通过 `npm --prefix runtime run cases -- <command>` 列出、捕获、复核案例和生成/应用知识提案，默认案例目录为
`.data/knowledge-cases/`。确认根因必须关联报告中的源码/日志观测；新增知识保留 `authority: auto`，补齐现象入口后通过
整库校验才会写入。一次固定集通过不代表 provider parity 或线上诊断质量已通过验收，运行入口和指标边界见 [`docs/triage-feedback-and-evaluation.md`](../docs/triage-feedback-and-evaluation.md)。

旧 Python Agent 的 `harmony_agent.knowledge_feedback` 命令只适用于旧案例格式，不会读写 Mastra 案例归档；
历史人工反馈与评估背景见[修复与验证说明](../docs/triage-feedback-and-evaluation.md)。
确认根因后再按知识维护规则提炼：
先核对相似条目，优先更新规范 ID；编辑适用范围、判据与例外后校验全库。新条目默认 `auto`，不自动提升来源
权威，不自动生成 `verified_at`。新增事实还应补充或更新关联现象及区分问题。
