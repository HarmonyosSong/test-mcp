# 条目格式定义

两个目录、两类条目，字段不同。`symptoms/<name>.md` 放现象，`facts/<业务域>/<name>.md` 放事实与判据。
文件名（去掉 `.md`）必须等于 frontmatter 里的 `name`，并且在整个知识库中唯一。

## 目录与业务域约束

- 事实必须放在一层业务域目录内；禁止 `facts/*.md` 平铺，也禁止继续嵌套子域。
- 现象保持 `symptoms/*.md` 平铺，方便同一现象关联多个业务域。
- 业务域代码遵循 `^[a-z0-9][a-z0-9-]*$`，已有分工见 [README](README.md#目录)。优先复用现有域；
  确有新业务范围时新增域目录并更新分工表，不需要修改 Python 枚举。
- 每条知识只保留一份。跨域通过 `domains` 和 `[[name]]` 关联；跨端用 `applies_to` 表达，不复制条目。
- 分类移动不改变 `name`。`name` 是稳定引用 ID，不把目录拼进 ID，也不因归属调整而重命名。
- 内容目录只放条目；维护说明放知识库根目录，避免被加载器误认为条目。

## 公共字段

| 字段 | 必填 | 取值 | 说明 |
| --- | --- | --- | --- |
| `name` | 是 | kebab-case，`^[a-z0-9][a-z0-9-]*$` | 必须与文件名一致 |
| `kind` | 是 | 见下表 | 必须与所在目录匹配 |
| `domains` | 否 | kebab-case 字符串列表，不可重复 | 事实省略时从目录推导；显式填写必须包含所在目录业务域。现象省略时为未知，可填多个候选域 |
| `applies_to` | 是 | `harmony` / `ios` / `android` 的列表 | 适用端。是**过滤维度**，不是分区键 |
| `authority` | 是 | `official` / `internal-sop` / `code` / `ticket` / `auto` | 来源类型，帮助评估判据可信度；不代表本次故障已成立 |
| `updated_at` | 是 | `YYYY-MM-DD` | 最后修改日期 |
| `verified_at` | 否 | `YYYY-MM-DD` | 最后**人工验证**日期。**缺席表示从未验证过**；超过 180 天会告警 |
| `applicable_versions` | 否 | `"5.0-6.0"` / `"5.0-"` / `"5.0"` | 版本区间，闭区间。留空表示全部版本 |

### kind 的取值

| 目录 | 允许的 kind | 含义 |
| --- | --- | --- |
| `symptoms/` | `symptom` | 用户会怎么描述问题。检索入口 |
| `facts/` | `platform-fact` | 平台客观事实：权限模型、版本行为差异、限制 |
| `facts/` | `mapping` | 映射关系：现象→原因、错误文本→模块、业务实体→代码位置 |
| `facts/` | `experience` | 团队经验判断：排查优先级、阈值、排除规则。**会被证伪，只能作线索** |

### authority 的含义

`authority` 用于评估知识判据的来源，不能替代当前案例的观测：

- `official` / `internal-sop` / `code` —— 经核实且适用时可以提供业务或技术判据；
  `located` / `probable` 还必须引用当前实际输入日志或工具读取的源码观测，知识命中本身不够
- `ticket` / `auto` —— **只能作为待验证线索**，不能单独支撑正向结论
- `experience` 类型的条目无论 authority 如何，都只能作线索

三个高可信等级的适用面不同，别混用：

| 等级 | 证据是什么 | 不能证明什么 |
| --- | --- | --- |
| `official` | 官方文档、平台规范 | 项目里的实际用法 |
| `internal-sop` | 内部 SOP、已确认的工单结论 | 未经核对的代码现状 |
| `code` | **随版本发布的代码本身**（引用文件与符号） | 代码之外的服务端行为、别的仓库 |

`code` 是给"跨仓库接缝"和"实现即事实"这类知识用的：当结论来自本仓库代码，就写 `code` 并把
文件路径、符号名写进正文，不要含糊地标成 `internal-sop`——那会让人以为有人核对过工单。

`auto` 是**未经人工验证**的等级，包括模型凭常识写下的结论和未核对的推断。它允许入库，
但必须能被一眼认出：不要给它填 `verified_at`，校验器会对高等级却缺 `verified_at` 的条目告警。
用常识凑出来的条目留在这里，比删掉更有价值——它至少框住了候选空间，前提是没人把它当结论用。

## 现象条目（`symptoms/*.md`）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `symptom` | 是 | 主索引键。写成用户的原话，不是术语 |
| `aliases` | 否 | 同义表达列表。用户不会按你的用词提问，这里要写全 |
| `description` | 否 | 一句话补充说明，检索结果里展示 |

正文建议包含这四节（不强制，但强烈建议）：

```markdown
## 通用原因（三端共有）
按历史工单频率排序。三端共有的原因**只写一份**。

## 端特定原因
### harmony
### ios
### android
按端分节。原因相同、实现不同的，不要拆——差异写进对应的判据条目。

## 区分它们需要什么
按顺序列出问什么、看什么，每一步说明能砍掉哪些候选。
这一节通常比原因清单本身更有价值：输入是模糊的，先问对问题比先查更省事。

## 注意
已知的过期、例外、易误判情况。
```

## 事实条目（`facts/<业务域>/*.md`）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `description` | 是 | 一句话说清这条事实是什么 |
| `aliases` | 否 | 检索用的同义词，和现象条目的 `aliases` 同一个意思 |

`aliases` 在事实条目上同样重要：用户不会说「采样率回落」，他只会说「戴着耳机就失败」。
把用户的原话写进来。

正文建议：**事实陈述 / 判据（怎么确认它成立）/ 例外**。

例如 `facts/contract/order-contract-agreement-sources.md` 可以声明
`domains: [contract, order, payment]`。`shared` 表示真正共用的事实，并在指定任何业务域时享有同分优先级。
业务域只影响同分排序，不替代文本匹配、不排除其他域、不证明根因，也不替代端与版本适用性判断。

## 引用语法

现象条目正文里用 `[[条目名]]` 引用事实条目：

```markdown
6. **蓝牙耳机采样率回落** —— 见 [[harmony-audio-samplerate-fallback]]。
```

现象和事实都可以跨业务域引用事实，只允许使用全库唯一的 `[[name]]`，不能引用现象，不能写目录路径。
校验器检查重复 ID、悬空引用及引用目标类型；条目迁移业务域后，原有引用继续有效。

## 多端怎么写

判断标准：**用户说这句话时，三个端指的是同一件事吗？**

- 是 → 一份条目，`applies_to` 写全三端，原因按“通用 / 端特定”分节
- 不是（比如根本是不同产品线）→ 才拆成条目

**共享的是“原因空间”，分端的是“证据和判据”。** 守住这一句，就不会退化成三个互相不一致的库。
