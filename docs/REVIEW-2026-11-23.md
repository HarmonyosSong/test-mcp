## 0. 结论速览

自 9-24 以来仓库完成 Python→Mastra TS 迁移（单 de-orchestrated loop）、新增 code-index /
log-mcp / version-registry / 知音楼 IM 渠道 / Compass A2A 协查 / 案例自动归档。**主链路已经
在真实使用**：11 月 47 个 web 会话，log-mcp 拉日志、学员信息、A2A 协查、源码核对都能跑
（§2）。旧三处 P0 两处已修复、一处部分修复（§3）。

**当前最重的问题不在代码断链，而在知识闭环空转与检索质量**（§4）：

- P0-a 案例→复核→条目的后半链**从未运行**：114 个归档案例 0 复核、0 提炼。
- P0-b 知识检索生产零命中率（剔除测试污染后）11 月仍 44%（lookup）/61%（search），
  top-1 被泛化条目占据；retrieval v2 实验目前不能接班（实测反向退化 55%）。
- P1-c code-index 只覆盖 6 个模块，且「人文书房」被错挂为英语书房的别名，查询被确定性
  误导到错误源码。
- P1-d 测试套件把 261 条夹具查询写进了生产查询日志（占全量 1/3）。

  165010784572 刘佳怡 支付过程中出现问题2」，agent 查学员信息（uid、年级）、设备与版本

## 4. 本次发现的问题（按严重度）

### P0-a 知识闭环后半段从未运行

`.data/knowledge-cases/` 114 个案例：**0 复核（review 全为 null）、0 提炼
（knowledge_entry 全为 null）**。capture/review/draft/apply 是人工 CLI，无人执行。
知识库从 68 → 91 条目的增长全部来自手工编写与 9 月底 audit 实验（`.data/knowledge-audit*`
等 7 个实验目录），不是「真实排查→案例→条目」的自举。9-17 拍板的「知识库是最痛点、
靠使用自举」这条核心机制，**设计上已接通（终态自动归档）、运营上仍是断的**——
与 P0-b 互为因果：11 月真实高频问题（绘本白屏、磨耳朵停止、讲义邮寄转圈、人文书房、
跨报去结算）在知识库里没有条目，因为它们从未被复核提炼。

### P0-b 知识检索质量：零命中率仍高，top-1 被泛化条目占据

剔除测试污染（P1-d）后，11 月真实查询 168 条：零命中 91（54%）；分工具
`lookup_issue` 44%（32/72）、`search_knowledge` 61%（59/96）。

有命中的 77 条里 top-1 分布：`app-search-scan-web` 21、`cloudlearn-terms-vs-user-words` 13、
`classlearn-spoken-island-entry` 12、`pangu-qr-payment` 8——**泛化/词表类条目靠词汇重叠
占据 top-1**，与查询语义无关（实测：绘本白屏类查询 top-1 多为词表条目；
「磨耳朵循环停止」命中口语岛条目 score 3.0 满分）。9-24 记过的「支付失败→盘古二维码」
误命中至今仍在发生（pangu-qr-payment top-1 出现 8 次）。

retrieval v2 不能接班（实测，附录 A-3）：在 75 条生产零命中查询上只召回 4 条；
在生产已命中的 74 条上反而丢 41 条（55%）。v2 配置注释自承「初始实验值，不是已测得的
生产最优」，生产默认仍 legacy 是对的，但意味着**检索质量短期内没有已验证的改善路径**。

### P1-c code-index 覆盖 6 模块 + 错误别名误导

`code-index/modules.json` 只定义 6 个模块规则（跨报/磨耳朵/英语书房/首页/登录/支付），
生成 96 条索引（6 模块 × 多版本 × 3 端）。绘本、讲义邮寄、人文书房、识图、退费等
11 月真实问题**不在覆盖内**（零命中属预期）。更严重的是 english-library 规则的别名
`['英语书房','人文书房','书房','英语阅读']` 错挂「人文书房」：实测「人文书房答题录音…」
「人文书房首页书籍解锁」确定性命中英语书房条目（score 6），把排查引向
`ClassLearnEngLibraryH5Page.ets` 等错误源码。另外同模块多版本副本挤占结果位（top3 全是
同一条目的不同版本）。

### P1-d 测试污染生产查询日志

`runtime/test/cases.test.ts` 的夹具输入「页面进入后闪退」：2026-11-03 → 11-23 共 261 条
`search_knowledge` 记录写入 `.data/knowledge-queries.jsonl`（conversation_id/message_id 均为
null，median 间隔约 7 分钟，末条正是本次验证跑 `make test-runtime` 的时刻）。
占全量 775 条的 1/3，直接扭曲任何基于该日志的命中率统计与未命中分析
（9-24 已指出 `query_log.py` 漏统 `lookup_issue` 未命中，如今日志本身又混入测试流量）。
测试应写临时日志文件（`HARMONY_AGENT_KNOWLEDGE_QUERY_LOG` 指到 tmp）。

### P1-e 评估面三处薄弱

1. 数据集 3 case/4 轮，且提示词仍引用已退役的 `submit_diagnosis_report`（见 §3）。
2. `unsupported_conclusion` 依设计需人工审阅，实际 0 assessed——最重要的「结论无支撑」
   指标从未被填过。
3. decisions/0002 要求的指标采集，目前只有 token/耗时/工具计数自动落盘，质量指标靠人工。

### P1-f 上下文全量回放，无体积控制

`historyFor`（`runtime/src/diagnosis/agent.ts:165-178`）把全部 completed 历史（含校验打回的
重试轮）以纯文本传入，无截断/窗口/摘要；`MODEL_CONTEXT_WINDOWS` 只是元数据未用于裁剪。
实测 corroboration：live-eval 的 2 轮案例 input 已达 42.7K token。9-24 记过的
「thinking 回放」已消除（无 reasoning 回放），这是改善，但长会话成本会随轮次线性膨胀。

### P2 其他确凿问题

- **g 手机端切换是死代码**（9-24 旧问题仍在）：`styles.css:3278+` 的
  `[data-mobile-view]` 媒体查询完整，但 web/src 全部 TSX 无任何元素渲染 `mobile-view-nav`
  或设置该属性——≤599px 侧栏隐藏后无任何 UI 切回，会话列表在手机上不可达。
- **h spec 过时**：`spec/compass-a2a-integration.md` §1 仍描述已退役的 Supervisor/分支架构，
  且声称「模型没有可绕过 Supervisor 的自由文本工具」，与 `consult_compass` 现实直接矛盾；
  README.md:24 仍把它作为接入契约引用。
- **i verdict 无锚点 12/66（11 月）**：校验重试 ≤2 次后放行 verdict=null，下游统计/标签缺失。
- **j `applicable_versions` 仍 0/91 填写**（9-24 旧问题原样存在）。
- **k `.data/conversations.json` 是 10-10 陈旧快照**，真实存储在 runtime.db；
  旧文件不删不改，任何按旧路径做的分析都会拿到错的总体（本次复评第一步就踩到）。
- **l failed 轮也归档进案例池**且归档失败 `allSettled` 静默——靠人工 review 时清洗，
  设计如此但值得知晓。
