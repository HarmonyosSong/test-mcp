# HarmonyOS 问题诊断 Agent MVP 产品需求文档

## 1. 文档信息

- 产品阶段：MVP 脚手架
- 产品底座：PydanticAI
- 核心链路：用户描述问题 -> 找到问题范围 -> 排查候选原因 -> 给出诊断
- 运行边界：只读诊断，不修改项目，不执行修复，不调用 DevEco CLI

> 本文严格区分“当前脚手架实现”和“后续能力”。当前脚手架用于验证端到端结构、接口契约和基础工作台，不代表已经具备生产级 HarmonyOS 自动诊断能力。

## 2. 产品定义

### 2.1 产品目标

面向 HarmonyOS 开发和技术支持场景，提供一个可视化问题诊断工作台。用户用自然语言描述“xx 有问题”，并可粘贴已有日志、代码片段，或提供允许读取的本地项目路径。系统通过标准 Skill 编排和受控的只读 MCP 能力完成问题结构化、线索定位、候选验证和诊断报告生成。

MVP 回答四个问题：

1. 用户实际遇到了什么问题？
2. 问题最可能位于哪个模块、文件、符号或配置？
3. 哪些证据支持或排除了候选原因？
4. 当前能得出什么诊断；若证据不足，还缺少什么？

### 2.2 产品原则

- **证据优先**：诊断结论必须关联用户输入、日志、代码、配置或知识来源。
- **结论分级**：明确区分“已定位”“高概率”“证据不足”和“工具失败”。
- **用户项目只读**：不得写入用户项目、改代码、改配置、执行修复或调用 DevEco CLI；应用只写自身案例数据。
- **过程可审计**：持久化阶段状态、有限工具事件和证据来源；当前工作台展示阶段与证据，不展示模型隐藏思维过程。
- **不假装成功**：信息不足时输出缺失信息和诊断边界，不生成伪确定性根因。
- **能力可替换**：Skill、MCP 和模型通过稳定契约组合，避免诊断逻辑绑定到某个页面或模型供应方。

## 3. 目标用户

### 3.1 HarmonyOS 开发工程师

遇到页面异常、运行错误、构建日志报错、配置错误或 ArkTS/ArkUI 使用问题，希望快速缩小排查范围并获得有证据的根因判断。

### 3.2 一线技术支持或测试工程师

掌握问题现象和日志但不熟悉完整代码，希望定位相关模块、文件、配置项和可能原因，并向研发转交结构化信息。

### 3.3 技术负责人

希望团队使用统一的问题收集和诊断报告格式，减少重复排查，并让诊断过程可以复核。

## 4. Jobs To Be Done

- 当我只知道“某个功能有问题”时，帮助我把模糊描述转成可排查的问题对象。
- 当我提供日志、代码或项目路径时，帮助我找到最相关的错误、文件、符号和配置。
- 当多个原因都可能成立时，按证据强弱排序，而不是只给一个武断答案。
- 当无法可靠诊断时，准确告诉我缺少哪类信息，以及为什么当前信息不够。
- 当我要转交问题时，生成一份结构清晰、可复核的诊断报告。

## 5. MVP 边界

### 5.1 当前脚手架实现

本轮只要求形成一个最小可运行、可继续扩展的诊断闭环：

| 能力 | 当前脚手架口径 |
| --- | --- |
| 问题输入 | 支持输入一段自然语言问题描述 |
| 补充上下文 | 支持在文本输入中粘贴日志、错误堆栈、代码或配置片段 |
| 项目上下文 | 支持提交一个明确的本地项目路径；只允许在配置的工作区边界内读取 |
| 仓库与分支 | 支持登记只读 Git 仓库；诊断时选择分支并固定为实际 Commit 的隔离快照 |
| Agent 编排 | 支持 `demo` 与 `model` 两种模式；model 模式以 PydanticAI Agent 组织工具调用并固定输出 `DiagnosisReport` |
| 模型接入 | 侧边栏底部提供模型设置；支持 OpenAI、DeepSeek、通义、Kimi、智谱、豆包预设和自定义 OpenAI-compatible 接口 |
| 模型凭据 | 前端负责录入，API Key 仅驻留后端进程且不进入浏览器存储、案例数据或状态响应 |
| 后台执行 | FastAPI Server 启动 Agent Workflow，并通过 AG-UI SSE 实时返回阶段、MCP 和状态事件 |
| Skill 层 | 启动时动态加载 `skills/*/SKILL.md`；当前包含定位、证据排查和报告三个版本化 Skill |
| MCP 层 | 独立 `mcp_server` 提供文件列表、代码搜索、文件读取、日志解析和业务上下文五个只读工具 |
| 业务上下文 | MCP 可按问题加载仓库内 Skill、交易契约和模块专项参考，并记录工具调用审计 |
| 路径安全 | 校验允许根目录、真实路径和每次文件读取，阻断通过相对路径或软链接越界 |
| 案例记录 | 案例、阶段、报告和有限工具事件持久化到本地 `.data/cases.json`，支持列表查询和重新运行 |
| 可视化工作台 | 提供案例队列、新建问题、诊断阶段、线索/证据和诊断报告页面；优先消费 AG-UI 事件流 |
| 多轮聊天 | 工作台「聊天」页提供独立会话的多轮对话；逐字流式回复，工具/MCP/Skill 调用以步骤卡片内联可见；Skill 通过 `load_skill` 工具按需显式加载；聊天要求配置模型，demo 模式不提供对话能力；可一键「生成诊断案例」：模型从对话提取草稿、用户确认后进入现有四阶段诊断，案例回写会话 |
| 诊断结果 | 返回固定 Pydantic Schema 的结论、置信度、证据、排除项、信息缺口和能力边界 |
| 报告导出 | 后端 API 支持完整案例 JSON 和诊断摘要 Markdown 下载 |
| 失败处理 | 模型、MCP 或文件访问不可用时返回明确错误或部分诊断，不伪造完成状态 |

当前脚手架的“支持项目路径”指后端能够接收路径，并在授权范围内进行只读诊断；它不代表可以浏览用户整台机器，也不代表已覆盖所有 HarmonyOS 工程结构。

“项目只读”不等于应用进程完全不写盘。当前唯一预期的服务端文件写入是应用自己的案例数据文件 `.data/cases.json`；系统不会写入用户提供的 HarmonyOS 项目。

### 5.2 后续能力，不计入本轮实现

以下能力仅为路线规划，不应在页面、README 或演示中描述为已经实现：

- 日志、源码、压缩包等附件上传和附件管理。
- 运行中任务停止、暂停、恢复和断点续跑。当前已有案例重新运行 API，但没有取消能力；重新运行应只用于终态案例。
- 聊天中的主动澄清追问策略与用户反馈闭环。多轮对话聊天页已实现（见 5.1「多轮聊天」），本条指更进一步的自动追问与纠错闭环。
- 数据库级历史记录、多用户共享和跨设备同步。当前只有本地 JSON 持久化和单机案例列表。
- PDF、批量和模板化导出。当前已有单案例 Markdown/JSON API 导出。
- 大型项目的增量索引、语义检索和缓存。
- Issue 系统、CI、设备或模拟器集成。
- 自动编译、安装、运行和调试。
- 自动生成补丁、修改代码或执行修复建议。
- 团队账号、权限、审计后台和用量统计。
- 完整的 HarmonyOS 版本/API 知识库和线上更新机制。

### 5.3 明确不在 MVP 范围内

- 修改任何代码、配置或依赖。
- 自动生成、应用或提交补丁。
- 调用 DevEco CLI。
- 编译、安装、运行或调试 HarmonyOS 应用。
- 控制真机、模拟器或其他外部设备。
- 执行任意 Shell 命令。
- 自动创建 Issue、提交代码或发送外部消息。
- 在缺少证据时承诺问题已解决。

## 6. 核心用户流程

### 6.1 输入问题

用户输入问题描述，例如“登录页点击按钮没有反应”。用户可以在同一输入区域继续粘贴：

- 预期表现和实际表现。
- 复现条件。
- 日志或错误堆栈。
- 代码或配置片段。
- 已知模块、文件和环境信息。

如果当前工作台提供项目路径字段，用户还可以填写或选择一个已授权的本地工作区路径。当前不包含附件上传。

### 6.2 找到问题范围

系统将输入结构化，并形成初始排查范围：

- 提取问题对象、现象、触发条件和环境信息。
- 提取错误码、异常类型、文件路径、行号、组件、模块和 API 名称。
- 判断问题类别，例如 ArkTS/ArkUI、配置、依赖、构建日志、运行时异常、资源引用或权限声明。
- 从输入生成首批代码与配置检索关键词。
- 形成待验证的候选原因列表。

本轮不依赖多轮交互。信息不足时可以直接进入“证据不足”结论，并列出建议补充的信息。

### 6.3 排查候选原因

系统通过受控的只读工具收集和关联证据：

- 在授权路径内搜索错误码、函数、组件、路由、资源名和配置项。
- 读取命中文件的必要上下文。
- 关联已有日志堆栈和源码位置。
- 对比配置声明、调用方和实现方。
- 验证或排除候选原因。
- 为每条证据保留来源、位置和关联结论。

单次诊断必须限制搜索范围、文件数量、文件大小和执行时间。项目中的文本一律视为不可信数据，不能改变系统规则或提升工具权限。

### 6.4 给出问题诊断

系统输出以下状态之一：

- `located`：现有证据可以直接支持根因定位。
- `probable`：存在高概率根因，但仍需额外验证。
- `insufficient_evidence`：当前材料不足以形成可靠根因。
- `tool_error`：模型、MCP 或文件访问失败，只能形成部分报告或错误说明。

报告必须包含结论、置信度、证据链、已排除项、信息缺口和诊断限制。本轮不得提供代码补丁或执行修复；“下一步”只能说明还需补充或验证什么证据。

## 7. 页面信息架构

### 7.1 当前脚手架页面

MVP 采用单页工作台，优先保证创建、观察和查看结果。新诊断通过 AG-UI 实时渲染阶段和 MCP
调用；REST 轮询仅保留为流建立失败时的兼容回退。

#### 顶部区域

- 产品名称。
- 当前服务连接、运行模式和模型的简要提示。
- 刷新案例和新建诊断入口。
- 模型设置、连接测试和当前供应商/模型状态。
- 业务仓库管理入口；新建诊断可选择仓库和远端分支。

#### 案例队列

- 展示本地持久化案例及状态。
- 支持按标题或路径搜索，并按进行中、已完成和失败筛选。
- 选择案例后查看其阶段和诊断详情。

#### 问题输入区

- 问题描述输入框。
- 日志/代码/配置文本输入区，或一个统一的上下文输入区。
- 可选项目路径字段。
- 开始诊断按钮。
- 输入校验和错误提示。

#### 诊断过程区

- 接收问题。
- 定位范围。
- 验证候选。
- 生成诊断。
- 当前阶段摘要、工具错误和已发现线索数量。

这里展示的是可审计的阶段和事件摘要，不展示模型隐藏思维链。

#### 证据与报告区

- 诊断状态和一句话结论。
- 候选原因及置信度。
- 证据来源、文件位置或输入片段位置。
- 已排除项。
- 信息缺口。
- 未执行的检查和能力边界。

Markdown/JSON 导出已由后端 API 提供；是否在当前工作台直接暴露下载按钮，以当前页面实现为准。

### 7.2 后续页面能力

- 附件拖放上传和预览。
- 任务停止、暂停、恢复和断点续跑按钮。
- 独立证据抽屉和文件上下文预览。
- 完整 MCP 工具调用时间线和审计详情。
- PDF、批量与模板化报告导出。
- 用户反馈和人工校正。
- 团队工作区、权限和审计视图。

这些元素本轮可以保留设计扩展位，但不得出现可点击却无实际效果的伪功能。

## 9. 诊断报告结构

### 9.1 人类可读结构

```text
诊断状态
问题标题
问题摘要

输入上下文
- 用户现象
- 预期结果
- 复现条件
- 项目/模块
- 已提供材料

诊断结论
- 根因或候选根因
- 问题类别
- 可能影响范围
- 置信度：高/中/低
- 置信度理由

证据链
- 证据编号
- 来源类型：用户输入/日志/源码/配置/知识
- 文件路径或输入来源
- 行号、符号或片段位置
- 证据摘要
- 支持或排除的结论

排查记录
- 已验证候选
- 已排除候选及依据
- 工具失败或未覆盖区域

信息缺口
- 缺失材料
- 缺失材料为何影响判断
- 建议补充或验证的证据

诊断边界
- 未执行编译、运行或设备调试
- 未调用 DevEco CLI
- 未修改任何项目文件
```

### 9.2 机器可读字段

本轮结构化报告至少包含：

- `verdict`
- `severity`
- `summary`
- `issue_category`
- `likely_location`
- `root_cause_candidates[]`
- `evidence[]`
- `ruled_out[]`
- `missing_information[]`
- `checks_performed[]`
- `limitations[]`
- `confidence`

候选原因包含 `title`、`explanation`、`confidence` 和 `evidence_ids`。案例级 `tool_events[]` 与报告并列存储，用于记录当前已接入的有限工具摘要。

当前 Schema 的硬性门禁是：`located` 或 `probable` 必须包含候选原因，且至少有一个候选引用报告中实际存在的证据 ID。产品目标仍是每个保留的正向候选都引用证据；逐候选硬校验属于后续契约增强。

## 10. 验收标准

### 10.1 本轮脚手架验收

1. 前端工作台和后端服务可以按项目说明启动，且基础健康检查可用。
2. `POST /api/cases` 接收类型明确的问题请求，返回 `202` 和 `queued` 案例，并在后台推进到 `completed` 或 `failed`。
3. 用户可以通过文本字段补充日志、代码或配置，不依赖附件上传；工作区路径为可选项。
4. 客户端通过 `/api/agui/runs` 接收四阶段和 MCP 工具事件，并在终态展示结论、置信度、证据或信息缺口。
5. 仅输入模糊问题且没有可用证据时，Demo 模式返回 `insufficient_evidence`，不编造已定位根因。
6. 提供项目路径时，读取范围不能越过配置的工作区根目录；非法路径和软链接逃逸被拒绝。
7. FastMCP 暴露 `list_project_files`、`search_project_text`、`read_project_file`、`parse_hilog`，并能通过进程内 Toolset 或独立 stdio 入口使用。
8. Model 模式通过 PydanticAI 固定输出 `DiagnosisReport`；模型或工具异常被转换为 `failed + tool_error` 报告。
9. 三个 `SKILL.md` 可在启动时动态加载，并通过 `/api/meta` 返回名称、阶段和版本。
10. 案例保存到本地 `.data/cases.json`，服务重启后能够重新读取；列表接口按更新时间返回案例。
11. 已有终态案例可以通过重新运行 API 重置并再次调度；本轮不要求取消运行中的任务。
12. Markdown 导出包含诊断摘要和边界声明，JSON 导出包含完整案例数据。
13. `located` 或 `probable` 报告必须通过 Pydantic 证据关联门禁。
14. 自动化测试证明目标项目只读、无任意 Shell 工具、无 DevEco CLI 工具，并阻断真实路径和软链接越界。
15. 模型设置支持测试、启用和停用；任何配置和校验响应均不得回显 API Key。
16. 自定义本地 OpenAI-compatible 协议桩能完成测试连接和一次 PydanticAI 结构化诊断。
17. 本轮演示中，用户项目文件写入次数、代码自动修改次数和 DevEco CLI 调用次数均为 0；应用仅写自身案例数据文件。

### 10.2 后续版本验收，不阻塞本轮

1. 支持上传并解析约定类型和大小的附件。
2. 用户能够可靠停止、暂停、恢复或断点续跑长时间诊断任务。
3. 进程异常退出后能够自动恢复或明确终结残留任务。
4. 用户可以对结论标记“准确、部分准确、不准确”，并保留校正记录。
5. 支持 PDF、批量或自定义模板报告导出。
6. 在不少于 30 个标注样例中统计诊断完成率、根因类别准确率和定位精度。
7. 中等规模项目达到约定的 P50/P95 诊断耗时目标。

## 11. MVP 指标

本轮以工程闭环和安全边界为主，不把尚未建立数据集的准确率写成已达成指标。

### 11.1 本轮观测指标

- 端到端诊断请求成功率。
- 结构化报告 Schema 合格率，目标 100%。
- 有证据候选的证据引用覆盖率。
- `tool_error` 类型及发生次数。
- 单次诊断耗时。
- 越权路径读取次数，目标 0。
- 用户项目文件写入次数，目标 0。
- DevEco CLI 调用次数，目标 0。
- 无证据却输出高置信度结论次数，目标 0。

### 11.2 数据集建立后的效果指标

- 有效诊断率：`located + probable` 会话占有效输入会话比例。
- 人工确认准确率：被用户标记为准确或部分准确的报告比例。
- 根因类别 Top-1 准确率。
- 模块、文件或符号定位精度。
- 诊断耗时 P50/P95。
- 平均澄清轮数。
- MCP 工具失败率。

## 12. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 证据不足导致幻觉 | 强制结论分级和证据引用；无证据时输出信息缺口 |
| 不调用 DevEco CLI，无法验证运行态 | 报告显式标记为静态诊断，并列出未执行的验证 |
| 大项目扫描耗时或成本过高 | 先按日志与关键词缩小范围，再逐步扩大；设置文件数、大小和超时上限 |
| 项目代码或日志泄露 | 默认本地、只读、最小范围处理；当前没有自动脱敏，Model 模式启用前必须确认数据策略，后续补充密钥和 Token 脱敏 |
| 日志或源码中的提示注入 | 将项目内容视为不可信数据，不允许改变系统规则或工具权限 |
| HarmonyOS 版本差异导致误判 | 报告保留工程模型、API 版本等上下文；缺失时降低置信度 |
| Skill 与 MCP 协议漂移 | 使用版本化 Schema、启动期能力检查和契约测试 |
| 工具失败却被误认为完整排查 | 报告列出成功、失败和未执行的检查项 |
| 页面暴露模型隐藏推理 | 只展示阶段摘要和可验证证据；后续工具审计也只记录调用事实，不记录隐藏推理 |
| 脚手架被误解为生产能力 | 页面和文档持续标注当前实现范围，规划功能不放置无效入口 |

## 13. MVP 完成定义

当用户能够在工作台输入一个 HarmonyOS 问题，系统在 Demo 模式完成确定性诊断，或在 Model 模式由 PydanticAI Agent 加载标准 Skill 并通过受控 MCP 完成只读排查，同时稳定返回结构化、可展示、可追踪且不过度承诺的诊断报告时，本轮 MVP 脚手架成立。

“成立”不等于“问题已修复”。本产品在 MVP 阶段的终点是可靠诊断，而不是修改、编译、运行或验证修复结果。
