# 演进路线：从鸿蒙诊断脚手架到多端排查 Agent

> **历史路线图说明（2026-11-03）**：本文记录早期 PydanticAI/Agent runtime 的产品演进思路，保留其知识库、证据和多端产品目标。当前用户-facing Agent 与 HTTP 服务已经迁移到 `runtime/` 的 Mastra 实现；本文的阶段状态、规模数据、`agent/`/`server/` 路径和旧测试数字不是当前状态或验收依据。当前阶段、实现路径和未完成项以 [`mastra-runtime-migration-spec.md`](mastra-runtime-migration-spec.md) 为准。

2026-09-17。这份文档给动手的人看：现在做什么，后面每个阶段做什么、做到什么算完。全局原则三条：最小改动，不动无关文件；证据门禁 `require_evidence_for_positive_verdict` 任何阶段不许破；领域概念（端、业务线、阶段名）不写死进枚举、提示词或包名。每个阶段的验收都落到 `agent/evals/datasets/diagnosis_cases.jsonl` 的扩充上，它是验收标准，不是事后补的作业。

约束一条：工单数据拿不到。知识库冷启动只靠代码可核实的事实（`authority: code`），积累走「排查 → 案例 → 提炼条目」的自举闭环。没有统计先验，追问收窄就是核心机制，所以它在第一阶段。

## 2026-09-17 历史快照

截至 2026-09-17 已跑通：PydanticAI 鸿蒙只读诊断 Agent（描述问题 → 定位范围 → 排查证据 → 输出诊断）；Skill 声明式加载（`agent/src/harmony_agent/skill_runtime/`）；两个 MCP server（仓库、知识库），进程内与 stdio 共用同一份定义；AG-UI 工作台与回归集。知识库 1 条现象 + 9 条事实（5 条接缝层事实锚在 xesapp 真实代码上），检索服务 3 个工具 + CI 校验，77 项测试。此为历史快照，不代表当前 Mastra 迁移状态。

已知天花板两处：`agents/prompts.py` 写死「HarmonyOS 只读诊断助手」；`EvidenceKind` 没有 `knowledge` 类型。这两处在阶段 4 一并解开，之前不要绕道修。（原第三处 `StageKey`/`STAGE_ORDER` 四阶段枚举已随 2026-09-24 案例队列移除而消失：诊断统一为多轮对话单一路径，报告经 `submit_diagnosis_report` 提交并接受证据校验。）

## 阶段 0：排查助手补全（代码与离线回归已完成，真实模型效果待验收）

1. **追问能力进诊断流程。** 追问不做独立工具，写成 Skill 指令，参照 dev-agent 三个 Skill 的同一句：「有界定位仍无法唯一定位，再请用户补充」。触发条件来自现象条目的「区分它们需要什么」一节，答案要能收窄候选空间。聊天路径已有多轮能力，缺的是把追问变成诊断流程里的正式一步。
2. **修 `tool_error_behavior="failed"`。** 现在一次工具失败把整轮打死。改成失败预算制，参照 dev-agent 的 `ToolFailureBudget`：按轮累计上限（默认 10）、同一调用签名失败后禁止原样重试、上游标记瞬时故障才允许同参数再来一次。

验收：模糊输入（不带端、不带入口）的 case 能触发追问并收窄；注入工具失败的 case 不再整轮失败。

2026-09-17 实现记录：三个诊断 Skill 升至 0.2.0，接入现象知识库的区分问题；聊天复用历史
收窄，单次报告用 `missing_information` 承载追问。预检和本轮各工具集共享失败预算，默认 10，
拒绝相同失败签名重复执行；上游显式 `transient: true` 才允许重试一次。耗尽后关闭工具，
保留最终回答，失败审计及报告限制如实记录。证据门禁保持不变。

当前 PydanticAI 的 `ToolFailed` 会把失败结果交回模型，本身不必然中止整轮；实现通过统一包装
将工具异常交回模型、限制累计失败，并补上原先未保护的预检路径。
`diagnosis_cases.jsonl` 已增加无端/入口的两轮追问、工具失败恢复、预算耗尽和预检失败案例；
离线测试验证工具与历史传递合同，不代替模型行为验收。真实模型验收入口见 README 的
`HARMONY_AGENT_LIVE_EVALS=1` 命令。

## 阶段 1：检索层成熟度

从 dev-knowledge 搬三条设计，加一条消费侧复核，全部落在 `mcp_server/src/harmony_knowledge_mcp/`：

1. `SearchHit` 补覆盖度状态（`support_status` / `gap_reason`）：「定位到了」和「能回答」分开。
2. 检索结果加显式三态 `resolved` / `ambiguous` / `not_found`，取代现在的命中加分数。
3. 冻结检索基线：固定语料 + 「问句 → 期望条目」标注断言（参照 dev-knowledge 的 `retrieval-baseline.json.gz`），以后改检索算法不许盲改。
4. 消费侧合同校验：Agent 侧复核检索返回——`resolved` 必须恰好一个高置信候选、查询词原样回显、`not_found` 必须对应空候选，对不上按证据缺口处理。

验收：基线测试护住检索改版；三态接入证据门禁，`resolved` 之外的命中不进正向结论。

## 阶段 2：dev-knowledge 前置层

判责任侧，把 H5 / 服务端侧的问题路由过去。按「做厚」准备：只接它的 MCP（协议兼容已实测，`mcp==2.0.0` 与我们 `mcp>=1.29.1,<2` 协商到 `2025-11-25`），术语翻译自己做——把 `knowledge/facts/cloudlearn/cloudlearn-terms-vs-user-words.md` 的对照表变成机器可读的查询改写规则，消费侧校验复用阶段 1 的成果。不 fork，不复制它的内容。

收窄后的路由范围：只有命中人文阅读（`picture-expression` 等）和背单词（`recite-word`）的问题才路由；口语岛侧它没有内容，靠我们自己的接缝层条目。

待决：对方 Agent（dev-agent，`xes_enterprise_agent`）能否以服务身份开放调用。它有完整 HTTP 接口，但身份模型是 SSO 员工命名空间，是交互产品不是服务间 API。若合作谈成，前置层做薄成纯路由；谈不成就维持做厚。代码层面两条路都留口。

验收：回归 case 证明裸调风险被拦住——「朗读完没有分数」裸调对方 MCP 会返回错误 Topic 的 `resolved`，前置层必须改写查询并复核后才采信。

## 阶段 3：双受众输出

单一事实源加两个渲染器：先产出机器可读的结论结构（链路、候选、证据、缺口），再派生开发版（证据链、文件位置）和支持版（现象解释、下一步动作、需要收集什么）。支持版不给根因判断。不许两次独立生成，两次生成一定漂移。

验收：同一 case 的两版输出由同一事实源渲染，事实项一一对应。

## 阶段 4：Domain Profile 重构，然后扩端

把「端」抽成一份配置：阶段剧本、Skill 命名空间、工具集、术语表、知识库范围都进 profile，鸿蒙是第一份。这一阶段解开现状的三处写死。做完才动安卓和 iOS：新端条目入库前，把 `knowledge/` 从 agent 仓库独立成纯内容仓库。端在检索里是 facet，不是分区键，结构不用动。

验收：新增一份最小 profile（哪怕只是占位端）不需要改 `skill_runtime` 和 prompts 的代码。

## 阶段 5（明确后置）

实时数据源（日志、监控、链路 trace、变更记录、配置中心、DB）走 MCP，一类数据源一个 server；届时 `build_repository_toolset` 从「仓库检查器」泛化成「数据源连接器」。上下文管理等本地 JSON 撑不住多用户和长会话时再说。

## 知识库运营规范（贯穿所有阶段）

- 条目来源：真实排查案例提炼，确认过的根因才入库；第一次入 `auto`，重复确认后升级。
- 不入库的：源码位置、诊断中间过程、排查步骤、工单原文、未标 `auto` 的模型结论。
- xesapp 的 `harness_Engineering/knowledge/` 只引用不复制；dev-knowledge 的内容只路由不搬运。
- CI 校验（`harmony-knowledge-validate`）必须通过：断引用是知识库最常见的腐烂方式。
- **失效回写**：排查中候选被当前证据证伪时，案例记录证伪，条目跟着更新——已修复的原因圈 `applicable_versions` 上界（老版本用户还会遇到，不删条目）、刷新 `verified_at`、或挪进「注意」。证伪不回写，库只能靠 180 天告警被动腐烂。
- 退款、订单、支付类现象是目前完全空白的领域，xesapp 知识层里有现成不变量可引用（状态码不得凭字段名猜测），建条目时优先用。
