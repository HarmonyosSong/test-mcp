## 二、P0：现在就会让一次真实排查失败

### P0-1 前端「绑定仓库」拦截器会伪造一条「已绑定」的确认，会话其实从未绑定

用户只要在聊天里打「绑定 xesapp」这类话（含「绑定 / 登记」+ 别名），就被前端拦截：它**只做全局仓库登记，
从不把仓库绑到会话**，然后本地伪造一条助手回复「已绑定仓库 xesapp」。`POST /api/repositories`（登记）与
`bind_repository`（绑到会话、写 `workspace_path`）是两件事，前端只做了前者。

证据：
- `web/src/lib/repositoryBinding.ts:16-43`（硬编码 xesapp / xesapp_pad 两个仓库及其别名）
- `web/src/hooks/useChatSessions.ts:151-181`（拦截 → `registerRepositoryByName` → `appendLocalMessage`，从不调用会话绑定；
  `appendLocalMessage` 只改本地状态，**不落盘**）
- 真实会话指纹 `.data/conversations.json` 中 `conv-bc04a8daf5`：用户 1「帮我看一下 releaseV/20260825
  组合加购订单这方面的逻辑」→ 助手答「本会话未绑定项目工作区，我没有可用的文件读取/代码搜索工具」→
  用户 2「咱们不是绑定了一个仓库了」→ 助手仍说没有工作区权限。该会话 `repository_name: null`、`workspace_path: null`，
  且**两条伪造消息在 JSON 里查不到**（因为不落盘）——与拦截器的行为完全吻合。
  （该会话里的第二句不含仓库别名、不会被拦截，所以用户「以为绑定过」的那次操作是更早发生的；
  另一种可能是用户把设置弹窗里的「登记仓库」读成了「绑定」。两种解释都指向同一个缺陷：**登记与绑定在用户面前没有区分**。）

影响：这是排查链路的第一步。更糟的是用户被告知「已绑定」——**错误确认比直接报错更伤**，
因为用户会认为「是 agent 能力不行」而不是「我这步没做成」。
同一份知识日志里 `lookup_issue("组合加购")` 也是零命中，于是知识没覆盖、代码又查不了，这次提问无路可走。

建议（最小改法）：删掉前端这条拦截路径，让绑定走对话内的 `bind_repository` 工具（它已有 `ModelRetry` 引导、
快照复用与持久化）；前端只保留设置弹窗里的显式「登记」。顺带把硬编码的仓库表从 `web/` 移除——
那是领域内容，不该在客户端；登记成功后也应在会话里明确提示「还需在会话中绑定才能查代码」。

### P0-2 检索是「最长公共子串 ≥ 4 字」的纯字面匹配，真实问法约一半静默零命中

`term_score()` 只有三档：term 是查询子串(3.0)、查询是 term 子串(2.7)、最长公共子串 ≥ 4 字(0.5+0.5×长度)。
中文没有词边界，用户换个说法就只剩空数组，而**空结果与弱结果在契约上是同一个东西**。

证据（`mcp_server/src/harmony_knowledge_mcp/retriever.py:16-18,55-66`；实测按 `lookup_issue` 原判据，
脚本输出见附录 A）：

```
同一概念的两种问法，结果 0 命中 vs 3.0 强命中（本次独立复现，逐对验证）：

  错题本进不去    → 无命中      错题本在哪   → 3.0 error-book-entry-picai-only
  发票开不出来    → 无命中      开不了发票   → 3.0 c-end-invoice-pilot-subject
  账号登不上     → 无命中      登录遇到问题  → 3.0 login-registration-basics
  怎么转班      → 无命中      转班限制    → 3.0 course-swap-restrictions
  1对1约课失败   → 无命中      1对1报不了名  → 3.0 one-on-one-booking-error-codes
  作业答案不显示   → 无命中      （条目 handout-answer-not-shown 就在库里，只差「讲义→作业」两个字）
  退款不到账     → 无命中      （用户最常说的词，语料偏好「退费」）

量级：本次复核的 18 条真实话术 11 条零命中；另一轮独立自造的 30 条问法 15 条零命中（其中 8 条库里有对应条目）。
```

同时有反方向的错：`支付失败` → 2.7 强命中 `pangu-qr-payment`（盘古二维码这条极窄成因），
`钱付了没反应` → 命中 `handout-answer-not-shown`（讲义答案）。零命中会促使模型追问，
**误命中会让它顺着不相干的链路走下去**，危害更大。

建议（最小改法，不动算法结构）：① 给「3 字重合」补一档低于阈值的分，把 `MIN_SUBSTRING` 从硬门槛
改成打分曲线起点；② 把 `cloudlearn-terms-vs-user-words` 从给人看的对照表升成**机器可读的查询改写规则**
（退款/退费、换班/转班、课程表/课表、登不上/登录、讲义/作业——这条你原本就为 dev-knowledge 前置层计划过，
同一套机制直接服务本地检索）；③ 顺手校正打分口径的注释（`retriever.py:8` 写「字符二元组」，实现是最长公共子串）
与死常数 `MIN_SCORE = 0.6`（永远不生效，实际门槛是 4 字）。

### P0-3 知识库入口只有 3 条现象，65 条事实里 60 条是孤儿 → 「追问收窄」没有素材

实测：3 条现象条目**总共只引用 5 条事实**，`facts/` 下 60/65 条没有任何现象条目引用它。
`lookup_issue` 先查现象、不够强就回退全量事实（`mcp_server/src/harmony_knowledge_mcp/server.py:85-95`），
所以默认路径事实上变成了「在 65 条事实的长 description 里做子串匹配」。

影响：现象条目承担的是「用户语言 → 候选链路 + 区分它们要问什么」。入口缺位的直接后果是
**追问清单没有来源**——而你自己定的口径是：工单拿不到、没有统计先验，**追问收窄就是核心机制**。
现在这条机制在数据层是空的。

建议：不要试图一次补全，按「真实案例 → 现象条目」自举，先补 4 条把孤儿事实救活：
`退款/退费到账`（引 `self-study-course-refund`）、`优惠券为什么用不了`（引 `coupon-unavailable-reasons`）、
`老师/课程评价提交不了`（引 `appraise-sensitive-word-block` + `teacher-rating-system`）、
`进不了教室/上不了课`（引 `bixin-class-c-end-behavior` + `class-replay-and-cloud-listening`）。
退款、订单、支付恰好是你自己标为「完全空白但最重要」的领域，从这里起手最划算。

### P0-4 「排查 → 案例 → 条目」的自举闭环断了，而且断了两次

`docs/ROADMAP.md:70` 与 `LEADERSHIP_SHARE.md:73-74` 都把「确认的根因回流知识库」写成知识库增长的唯一方式。
但代码里：
- `89e24ba` 把承载它的案例队列整体删除。旧结构（`.data/cases.json`，6 条遗留案例）里**本来就有**
  `report` + `tool_events` + `resolved_commit` + `stages`，现在这些字段没有任何落点；
- `grep -rn "case_ids" agent server mcp_server web` → 0 命中（字段只作为死键留在旧 JSON 里）；
- 提交成功的 `DiagnosisReport` 只随消息存进 `conversations.json`，没有任何归档、导出或候选条目生成；
- 唯一剩下的数据入口是 `.data/knowledge-queries.jsonl`，**18 次调用全是开发时手测的同两句话**，
  且它只记录「问了什么、命中没有」，**不含结论**——因此无法直接长成「现象 → 原因」条目。
- 更实际的问题：该 CLI 只统计 `search_knowledge`（`mcp_server/src/harmony_knowledge_mcp/query_log.py:241`），
  而默认入口是 `lookup_issue`。实测日志里 `lookup_issue("组合加购")` 是 `hit_count=0`，
  **它根本不会出现在「条目建设清单」里**。

影响：知识库只能靠人工写条目，写哪些全靠猜——这正是「没有工单、没有统计先验」时最需要被机器补上的那一环。

建议（半天量级，三件小事）：
1. 报告提交成功后追加一行到 `.data/triage-cases.jsonl`：`{用户原话, verdict, 候选, 命中的条目 ID, 证据缺口, 时间}`——
   这就是当初 `cases.json` 里最有价值的那半张表，只是不再承担「案例队列」的流程语义；
2. `query_log.py:241` 改成 `entry.tool in {"search_knowledge", "lookup_issue"}`（一行），让主入口的未命中进入清单；
3. 给 `harmony-knowledge-querylog` 加一个「本次日志的候选条目草稿」输出（现象条目骨架 + 命中的事实引用），
   让「排查 → 案例 → 提炼条目」的人工那一步有草稿可改。

### P0-5 当前设计从未被真实模型跑过，且没有采集指标的手段

`ROADMAP.md:13` 自述阶段 0「代码与离线回归已完成，**真实模型效果待验收**」；`docs/decisions/0002:63` 自己定了规矩
「未配置或未执行真实模型评估时，不报告成本下降比例或诊断正确率提升」。现状：
- **全部 11 个真实会话都早于当前设计**：最晚一次真实使用是 2026-09-23 09:36，而单一路径 + `submit_diagnosis_report`
  的重构（`89e24ba`）是 2026-09-24 15:13。数据文件里消息字段根本没有 `report`，**提交过报告的会话 = 0**。
  也就是说：多轮对话 + 结构化报告 + 证据快照跨轮这一整套，目前只有离线脚本化模型验证过，**没有任何一次真实跑通记录**。
- 唯一走真实模型的测试 `agent/evals/test_stage_zero.py:168` 默认跳过，且只覆盖 **1 条** case；
- 验收数据集 `agent/evals/datasets/diagnosis_cases.jsonl` 只有 **5 条**（2 条 tool_failure、1 条 clarification、
  2 条端到端），clarification 用的还是 `tmp` 里现造的夹具条目；
- `0002` 要求的比较维度（正确定位率、无证据结论比例、合理追问率、模型轮数、总 token、工具载荷、
  重复调用、耗时）**没有任何采集入口**：`tool_usage` 只按消息存（11 个会话里只有 2 条消息带它），
  没有聚合、没有 CLI、没有基线文件。

影响：现在没有任何手段回答「这个 agent 到底准不准」，也看不出任何改动是变好还是变坏。
这是唯一一条卡住所有后续优化的前置条件——包括上面 P0-2/P0-3 的修改，改完也无从证明。

建议：写一个 `harmony-triage-eval` 脚本（放在 agent 项目，`prompts`/`tool_usage`/Skill 都在手边），
对固定 case 集跑一次真实模型，输出 `0002` 那张指标表 + 落盘一份基线 JSON；此后改检索、改提示词、
改 Skill 都有前后对比。不必先堆 case 数量，先把「能重复测」这条通路建起来。

## 三、P1：明确的功能性缺陷

### P1-1 手机上工作台不可用
`web/src/styles.css:2813` 在 `max-width: 599px` 下把 `.app-sidebar` 设成 `display:none`，靠
`.body-row[data-mobile-view=...]` 切换；但 `data-mobile-view` 与 `.mobile-view-nav` 在 `web/src/**/*.tsx`
里**零出现**（全仓只有 CSS 提到）。结果：窄屏既看不到会话列表，也没有切换入口，设置面板同样够不着。
对「一线支持人员在手机上问一句」这个使用场景是阻断。改法：把移动端切换补进 TSX，或先让 CSS 回退为可滚动侧栏。

### P1-2 助手回复不渲染 Markdown
`package.json` 无任何 markdown 依赖，`ChatThread.tsx:52,240` 直接把 `{message.content}` 塞进 `div`。
真实回复里 `**`、`` ` ``、代码块、表格都原样显示（`conv-bc04a8daf5` 的助手回复就以 `**当前限制**` 打头）。
对诊断报告这种结构化输出是明显的观感损耗。改法：引入一个轻量 markdown 渲染器，只处理加粗/行内代码/代码块/表格。

### P1-3 服务端会话「整体覆盖写」，轮次进行中的重命名会被静默回滚
`chat_stream.py` 在开轮时取一份会话副本，整轮结束后 `save(conversation)` 整体替换；
`routes/conversations.py:78-89` 的 `PATCH`（改标题 / 改模型覆盖）若发生在轮中，会被结束时的保存覆盖掉。
这是典型的 lost update，改成「按 id 取最新再合并被改字段」即可。
（并发的第二条消息有 409 保护，这块没问题。）

### P1-4 前端流式协议处理有两处真实缺口
把 `agui/client.ts` 原样打包后接一个本地脚本化 SSE 服务端，跑 6 个场景实测：
- 遇到未知 AG-UI 事件类型直接抛错中断整轮，**后续的终态事件（`STATE_SNAPSHOT`/`RUN_ERROR`）被丢掉**；
- 流被异常截断时静默保留 `streaming` 状态（实测结果 `{"final":"只有一半","status":"streaming"}`，没有抛异常），
  前端会一直显示「正在思考」。
同时事件负载只校验 `type`，字段靠 `as T` 断言。改法：未知事件类型改为忽略并记录；`streamChatMessage`
的收尾对账不只在 `catch` 里做。

### P1-5 `SearchHit` 不带 `verified_at`，一半条目的「未人工验证」在候选阶段不可见
校验器对 36 条条目给出「不能作为正向结论的证据」（`make knowledge-validate` 原文），但这个状态只出现在
`KnowledgeDocument`（`schemas.py:86-97`）里，候选列表 `SearchHit`（`schemas.py:64-83`）没有 `verified_at`。
模型最先看到的就是候选列表，「已核实」和「从未核实」长得完全一样。改法：`SearchHit` 加 `verified_at` 一个字段
（`retriever.py:138-157` 加一行），并在 `server.py:35-46` 的 INSTRUCTIONS 里补一句「`verified_at` 为空的高等级条目只作线索」。

### P1-6 `applies_to` 欠填 + `applicable_versions` 全空，多端查询被无故降权
64/68 条写 `applies_to: [harmony]`，其中 30 条正文明确在讲 iOS/Android/HD；`applicable_versions`
**0/68 条填写**（正文里却出现 `V7.95` 这类版本号）。检索用 `applies_to` 算 `end_match`，不匹配 ×0.4 降权，
工具又告诉模型「`end_match` 为 false 只能当线索」。于是**用户主动提供端信息反而更有害**：
`lookup_issue("学习报告看不到", end="ios")` → 2.5×0.4=1.0 且被标成线索，不带 `end` 时是 2.5 的正常命中。
这条直接影响「先做鸿蒙、逐步扩多端」的路：多端话术一进来就被自己的降权规则压掉。改法：30 条做一次批量 review，
判据用条目正文自己的口径；`applicable_versions` 先回填正文里已有版本的那 12 条。
（分端版本区间是 schema 变更，可与阶段 4 的 profile 一起做，本次不必动。）

### P1-7 thinking 每轮原样回传，占请求体约 15%
`trim_messages_state` 只截 `tool-return`、只按整轮淘汰，**对 `thinking` 完全无感知**。
拿真实会话实测（脚本见附录 B）：`messages_state` 26 条中 13 条带 `reasoning_content`，
映射成请求体后 115,166 字节里 16,150 字节是回放的思维链；删掉 thinking 后 **98,383 字节（−14.6%）**。
持久化层面：`.data/conversations.json` 里 `messages_state` 占 73.7%，thinking 占其 16.8%。
这不是 bug（pydantic_ai 的 profile 行为，DeepSeek 系还要求回填该字段以免 400），
但**成本是实打实的每轮支出**。改法：在裁剪逻辑里对非当前轮 thinking 做丢弃或压缩，
保留最近 1-2 轮（`models/openai.py:1627` 的回填会兜住字段缺失），并留一个开关。

### P1-8 输入侧硬上限 + 无附件，真实材料进不来
`SendMessageRequest.content` 上限 20,000 字符（`domain/conversation.py:107-113`），前后端都**没有**任何
文件/图片/粘贴附件通路（全仓 `grep UploadFile|multipart|attachment` → 0 命中；前端无 upload/paste 处理）。
线上排查现场最典型的输入是一张截图或一整份 hilog，而 `parse_hilog` 要求用户把日志**粘进对话框**——
二十万字符级的 hilog 会被 422 直接拒掉。改法：先放宽文本上限，再加一个「上传附件 → 落盘为只读材料 →
以 USER 来源登记证据」的最小通路（证据账本已经能承载，缺的只是入口）。
