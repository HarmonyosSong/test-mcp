# 非向量检索 V2 继续评测：2026-09-28

**结论：当前 V2 有召回与速度收益，但不能切换为默认检索。** 在用于词表建设的样本上改善明显；新增压力问题暴露出更大的库外误召回面。独立替换预览选择有可分离的收益，适合优先继续验证。

复跑确认：按“现在再试一下”的请求重新执行了 68 个新增测试项的双模式查询，以及每模式五批、共 280 个热查询。代码与知识摘要均未改变；全部候选、分数、正文选择、状态及快照 ID 与上一轮一致。此次 p95 为 legacy 37.0ms、V2 18.5ms。质量结论不变，详见 [复跑摘要](retry-summary-2026-09-28.json)。

## 1. 评测对象与方法

- 代码：`6eed7df`，包含 V2 引擎及 F 阶段两轮词表修改；当前默认模式实测为 `legacy`。
- 本次没有修改生产检索、词表、知识内容或运行配置，没有新增模型调用。
- 原 153 条查询分别通过真实 MCP 跑 legacy/v2；另外新增 32 条正例、24 条负例和 12 条合同探针（规范 ID、否定/比较、标点与符号边界），共 **221 条不同的测试项、442 次配对查询**。原脚本还额外运行每种模式各 24 次症状主描述探针。
- 新样本在首次运行前落盘冻结；看过语料和当前规则后编写，属于合成压力测试，**不是独立盲测或真实流量统计**。正例目标是相关事实，不是已确认根因。
- 已有 38 条挑战问题被用于 F 阶段补词，必须视为开发/回归集。此前审核清单将它们写成“真实问法泛化”，不应据此理解为真实工单或独立验证。
- 另测五批、每批 56 个固定问题、两种模式交替先后顺序，共 560 次热查询；初始化单列。
- 正文选择 B：保留真实 legacy hits，只离线调用新选择器，单独计算预览收益；不声称测得 B 的 MCP 延迟。

数据：[新增冻结样本](cases-v2-followup-2026-09-28.json)、[完整结果归档](results-v2-followup-2026-09-28.json)。归档包含逐题命中、预览、分数、状态、源文件与规则摘要、知识文件 SHA256、性能批次和边界探针。

新负例里，V2 消除了 1 个旧误召回，但新增 6 个误召回，净增加 5 个。这个压力集刻意覆盖近期新增词的碰撞风险，不能把 19/24 外推为真实流量错误率，也不能据此断言最终 Agent 诊断错误 19 次。

新增误召回的六个实例：

| 问法 | 触发特征 | V2 返回的无关内容 |
|---|---|---|
| 附近有没有二十四小时营业的药店 | nearby | 班级筛选、附近教学点 |
| 香港明天的天气会不会下雨 | region | 教室地点、注册地区 |
| 澳门有哪些值得游览的景点 | region | 教室地点、注册地区 |

其他仍存在的误召回包括腾讯会议晨会、外部优惠券/劳动合同/发票、银行人脸、B 站回放、抖音作品等。19 条误召回中 15 条状态为 ambiguous，**4 条仍为 leads_found**，其中“GitHub 搜索不出来我的仓库”依靠意图短语获得 0.75 分。把短语命名为“审核意图”不能消除其跨产品通用性。

这说明只把“白屏、没有分数”降为通用状态还不够；新加入的对象和意图短语同样需要辨识力与语境检查。词表注释中的“负例验证通过”只对当时那些具体负例成立，不是该词没有碰撞风险。

## 5. 可复现的实现与设计差距

### 5.1 人类语言通道仍跨边界粘词

`retrieval_rules.py::analyze_query` 将标点归一化成空格后执行 `normalized.replace(" ", "")`；条目侧也如此。

- `合，同` 被识别为合同；
- `发，票` 被识别为发票；
- `课 堂 笔 记` 被识别为课堂笔记；
- `xnoteBackupTask` 和 `xnotebook模块加载失败` 把英文标识符内部的 xnote 当作授权对象。

已注册技术符号的专用通道则拦住了 `evaluationCheckViewExtra`、`foo_evaluationCheckView_bar`、`fromTaskExtra`。因此边界修复是部分完成，不能用这三个符号测试通过来证明全部通道合规。

8 个负向合同探针有 4 个返回候选。其中一题同时含“附近”和被拆开的“发；票”，它因组合分数不足而空返回，不能把这个空结果解释为标点处理正确。边界缺陷的依据是前述干净最小例与实际抽取的特征。

### 5.2 规范 ID 入口未接通

`RetrievalEngine` 在条目侧把规范 ID 放入 `_symbols`，但查询侧只接收 `REGISTERED_SYMBOLS` 中的固定符号，未接收知识库规范 ID。

以下两个设计规定的精确入口均在 V2 返回空：

- `scan-feature-and-http-block`
- `learning-data-sharing-switch`

技术符号和规范 ID 是不同来源的锚点，必须分别覆盖查询侧与条目侧。

### 5.3 加入有效条件反而变成零命中

| 问法 | 登录注册事实的对象覆盖 | raw_score | 返回 |
|---|---:|---:|---|
| 家长注册培优账号时，手机号应该按八位还是十一位校验 | 1.0 | 0.55 | 有登录注册事实 |
| **香港**家长注册培优账号时，手机号应该按八位还是十一位校验 | 0.5 | 0.275 | 全部为空 |

“香港”被提升为独立 region 对象，查询对象分母扩大；目标事实的检索字段只匹配 phone。虽然通过 0.50 的对象资格门槛，但分数低于 0.35 又被拒绝。这里算法按公式运行，问题在于把地点限定当成与手机号并列的业务对象，以及资格门槛与分数门槛组合后的行为。

不建议通过直接降低全局阈值解决，否则会进一步放大库外误召回。应先修正特征类型、对象和限定关系，再做配对评测。

### 5.4 快照规则摘要遗漏限定规则

隔离进程内将 `UNIT_FACETS` 临时增加一个单位规则，确认 `analyze_query` 的输出改变，但 `rules_digest()` 不变；随后立即恢复内存变量，没有修改文件。

当前摘要覆盖 concepts 和 REGISTERED_SYMBOLS，不覆盖 UNIT_FACETS。若这类规则变化没有同步人工更新 ENGINE_VERSION，就无法仅凭摘要区分行为。需要覆盖所有影响检索的规则及规范化配置；本探针证明的是摘要缺口，不是已发生过生产缓存污染。

### 5.5 一些设计阶段尚未交付

- `shadow` 仍明确报“当前不可用”，不是已经运行中的双路影子评估。
- 显式范围冲突规则、条目 profile 未接入；给对象词加 note 不会在运行时产生范围约束。
- `search_knowledge` 的 V2 日志未附 retrieval_status，无法像 lookup 一样按 V2 状态分析空结果。这是代码审查发现，当前主入口 lookup 的状态仍有记录。
- server 工具说明仍描述“先症状、弱命中再回退”，与 V2 实际统一竞争有差异；启用前需要同步。

以上不通过修改评测标签或减少负例分母来处理。

## 6. 门槛统计修正

`ablation.py` 原来检查旧负例时用 `split.startswith("existing")`，但真实 split 是 `negative`，`existing-*` 只是 case ID。它实际执行 `all([])`，因此会无条件返回通过。

本次仅修正这一处评测判断：读取 `negative` 分组；缺失分组也不通过。实际复跑旧负例确实为 0/6，所以六项数值门槛的结论仍为 **4/6**，并未因修正改变：

| 门槛 | 当前结果 |
|---|---|
| 原 38 问直接召回 ≥25 | 34，通过 |
| 原 38 问引用可达 ≥30 | 35，通过 |
| 原 38 问目标预览 ≥28 | 34，通过 |
| 原 16 负例误召回 ≤4 | 5，未通过 |
| 旧 6 负例零误召回 | 0，通过（这次实际检查） |
| 历史 10 改写召回 ≥3 | 2，未通过 |

另有设计工程门槛“既有 12+6 正例 top1 保持”，实际为 **17/18**，未通过。独立验收集与真实诊断对照尚未完成。不能把“接受残余风险”的讨论写成“发布门槛已满足”。

## 7. 性能与验证

环境：macOS 15.2 arm64，Python 3.12.14；本地进程内 MCP。性能复测时串行请求、五批交替模式，每种模式 280 个计时请求；每批另有预热调用。

| 指标 | legacy | 当前 V2/F |
|---|---:|---:|
| 热查询 p50 | 31.5ms | **17.1ms** |
| 热查询 p95 | 37.5ms | **18.1ms** |
| 服务构造/加载 p50 | 65.0ms | 68.2ms |
| 响应字符 p50 | 5507 | 5167 |
| 响应字符 p95 | 7491 | 6865 |

V2 查询更快，初始化略增。测量包括工具封装，不含网络和模型；服务构造计时不含客户端连接。此次未测 RSS 或真实诊断 Token，不据此宣称模型成本下降。

验证结果：

- 内容回归、知识 MCP、日志和 V2 测试合计 **124 passed**；其中生产内容测试使用默认 legacy，因此全绿不等于 V2 满足内容 top1 门槛。
- 按项目要求使用 MCP 环境单独复跑两组测试，**68 passed**。
- `make knowledge-validate` 通过，89 条内容，仍有 36 条既有验证日期告警。
- 新配对查询都遵守最多 3 hits、3 previews、4500 正文字及 `leads_only=true`；没有发现本组样本中被标为 relevant_reference 却不满足资格的正文。
- 知识内容与生产检索源码保持本轮评测开始时的状态；默认模式仍为 legacy。

## 8. 下一步顺序

1. 优先单独推进预览选择的验证与接入，保留原候选，明确它不解决原有误召回。
2. 修复边界粘接、规范 ID 查询和摘要覆盖，再做最小差异回归。
3. 把附近、地区、会议软件、弹窗等从无条件独立对象中重新审核；区分业务对象、限定条件和通用症状，别继续靠补更多完整问句维持指标。
4. 修复多条件查询的资格/分数组合，确保“提供更多有效信息”不会轻易丢失原相关事实。
5. 保持当前冻结样本作回归，另收未用于调参的真实工单；完成 shadow 与同模型诊断对照后，才重新讨论默认 V2。

本轮交付的是评测、可复现失败与一处评测脚本修正，没有顺带调优生产词表或启用 V2。
