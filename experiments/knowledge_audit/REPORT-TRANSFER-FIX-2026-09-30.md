# 错题上传检索修复与复测：2026-09-30

**结果：8 条冻结上传问法均能返回目标事实正文。默认 legacy 从 3/8 提升到 8/8，V2 从 0/8 提升到 8/8。**
原 154 项和后续 68 项未出现目标命中或负例拒绝指标退步，V2 另有一条表扬墙上传问题提升至 top1。
这些是已知开发回归样本，不是独立盲测或最终诊断准确率。

## 1. 实现范围

- 补齐“错题录入/上传错题”对象表达；知识条目的正文、别名、权威、验证日期均未修改。
- 区分输入（上传/录入/导入）与输出（导出），增加 PDF/图片介质限定。
  V2 沿用原权重和资格门槛；这些新增动作/格式本身不构成业务召回锚点。
- legacy 仅在原有候选同分且共享业务概念时，先按任务与介质覆盖排序，再应用域偏好。
  域仍不作硬过滤。原始分数不变，“上传 PDF”不会因为这段排序逻辑获得新候选。
- ranked 预览第二槽位由直接事实与合格一跳引用按相关性竞争，同分优先直接事实。
  引用遵循相同端/版本降权。最多三篇、每篇 1500 字符、线索标记与分页协议保持原预算。
- 默认仍是 legacy + legacy 预览；本轮没有改运行服务配置、重启服务或切换 V2。

设计细节：[技术文档第 19 节](../../docs/knowledge-retrieval-v2-design.md#19-2026-09-30同对象下的输入输出任务区分)。

下表仅统计 **8 条上传问法**，不混入另外两条入口资格正例。

另外两条入口正例仍是三配置均直接命中、返回正文。
四条专项库外负例仍误召回一条“公司报销系统上传发票PDF失败”，没有改善也没有增加。

例如“错题录入选了PDF，点完成后回到了应用首页”，修复前全部零命中；修复后三配置均能返回
`error-book-upload-file-types`，目标正文 1372 字符，未截断。命中提供核查判据，不能确认本次根因。

legacy 剩余两条未直接命中事实的问题是“扫描文档未上传成功”和“照片过大”。
因为上传现象已强命中，legacy 按原协议停在 symptom 范围；目标事实通过现象引用返回正文。
这属于预期的现象→事实路径，不能算作直接事实命中。

- 后续集与专项的实际 MCP 响应均满足最多三篇/每篇 1500 字符/`leads_only` 预算。

## 6. 剩余问题与复现

V2 仍未满足原发布门槛：压力负例须 ≤4/16，当前 5/16；历史改写须 ≥3/10，当前 2/10。
跨产品同名对象误召回、短别名触达和内容核验仍需单独处理。当前修复可改善默认模式的专项正文触达，
不足以据此把 V2 切成默认，也不能推出线上诊断质量已提升。

```sh
uv run --project server python experiments/knowledge_audit/run.py --mode legacy --out .data/kb-transfer-reproduce/legacy
uv run --project server python experiments/knowledge_audit/run.py --mode legacy --preview-strategy ranked --out .data/kb-transfer-reproduce/legacy-ranked
uv run --project server python experiments/knowledge_audit/run.py --mode v2 --out .data/kb-transfer-reproduce/v2
uv run --project server python experiments/knowledge_audit/recheck_v2.py --include-ranked-preview --out .data/kb-transfer-reproduce/paired
uv run --project server python experiments/knowledge_audit/check_error_book.py --out .data/kb-transfer-reproduce/error-book.json
```
