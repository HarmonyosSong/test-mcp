## 根因 1：证据淘汰与只读缓存不一致

`EvidenceLedger.add` 超过 120 条时 FIFO 删除，源码搜索每个匹配行都登记一条；
ID 的摘要还包含调用参数，不同查询命中同一内容也可能登记为不同证据。
当前轮报告尚未提交，关键文件读取已经被后续搜索结果挤出账本。

实录返回过但终态账本缺失的 ID：

- `ev-81afa39f3b2e9551`：WebView.ets:1。
- `ev-931ccfbc5b77e82d`：WebView.ets:94。
- `ev-ad7388cd2c6b3cb2`：WebViewV2.ets:25。
- `ev-6bd2b18a96705f1b`：PickerUtil.ets:100。

第三次报告的第一个 ID 就是第一项，错误文本仍称 was not observed。
账本终态正好 120 条，最早记录已经推进到第 22 次调用。
`ToolFailureBudget` 命中成功缓存时不执行 `BudgetedToolset.execute`，因此也不会再次 capture，
模型重新读相同文件无法修复丢失的账本状态。

优先修复：保护当前轮已交付的观测直到报告收尾；持久化阶段再做有界淘汰，
缓存复用必须保证引用仍有效或从可信缓存恢复。不能只放大 120，也不能放宽观测校验。

## 根因 2：裁剪方式迫使模型重读

`trim_messages_state` 将普通工具返回序列化后截前 4,000 字符，可能截断 JSON 和源码行。
本轮有 13 个返回被这样截断。示例：

- 第 8 次请求 WebView 1–200，持久化/请求前裁剪后的内容到约第 95 行中途停止。
- 第 9 次请求 94–340，裁剪后到约 171 行。
- 第 10 次请求 200–345，裁剪后到约 290 行，317 行 accept 分支仍不可见。

工具 metadata 中的 end_line 是原始读取范围，不代表模型实际看到的最后完整行；
当前没有结构化的 next_line 让模型继续读取。
前两次符号搜索已有关键行号，读文件却从文件头开始，更放大了问题。

修复方向：源码工具按字符预算返回完整行、实际起止行、truncated 和 next_line；
对这种有界结构化结果保留完整返回。默认围绕搜索锚点小范围读取，后续只取缺段。

## 根因 3：把“新内容”当作“调查有进展”

无进展判断只看空返回或整个结果的重复指纹；只要命中不同代码行就清零。
因此错题入口、分享页、半屏、退出登录等不同分支可以不断延长调查，
即使它们没有回答“这次为什么完成后返回首页”。
实录最终才追问“App 首页还是系统桌面/重启”“图片是否正常”。这些回答会直接决定要查路由还是崩溃。

修复方向：保留按子问题的查询范围与已排除路径；新搜索必须对应未决判断。
对需要用户观测才能区分的分支尽早追问。当前轮仍可先核实已有明确选择器线索，
但不应为了填补缺失运行时信息继续横向扫仓。

## 根因 4：报告接口要求模型重建可信元数据

报告需重传 ID、kind、source、location、excerpt，再逐项与账本验证。
本轮即使找回旧 ID，也仍有 location 不一致：观测位置是文件读取起始行，模型改成了其推断的具体行区间。
用户描述可以作为现象来源，但 input_texts 本身没有自动变成已登记、可引用的 USER 证据；
Evidence 的随机默认 ID 并不能完成这项登记。

修复方向：模型提交已观测 ID 与解释，可信元数据由服务端从账本组装；
需要更细范围时在完整观测文本中校验精确摘录。用户原文由运行时登记并显式提供 ID，
仍不得把 USER 或知识引用升级成机制级根因证据。

## 建议的本例调查路径

加载定位规则并读取必要业务限制 → 绑定已登记仓库 → 搜文件选择回调 →
按命中行读取选择器和过滤逻辑 → 有需要时确认实际承载组件 →
说明“PDF 可选”源码事实与“返回首页”未决边界 → 提前问能区分分支的一两个问题。

修复报告协议后，确有报告需要时一次提交；不应为了取回证据循环读同一文件。
可以将本例作为回归，比较相同结论质量下的工具数、模型轮数、累计 token 和报告成功率，
但尚未跑修复后真实模型对照，本文不承诺具体调用次数或节省比例。
